## 关键阶段准入

- **S1 → S2**：有当前代码事实基线；S1-A/S1-B 若仍在独立 PR，使用精确 SHA 与 PR 引用，不假装已合并。
- **S2 → S3**：完成 V1 目标、需求、设计、实现、成败和演进的有界覆盖；22 项旧问题被重新归因或明确待证；成功证据和正确拒绝同样进入复盘。**不要求修好旧 V1**。
- **S3 → S4**：历史需求、经验、技术实现、假设和未决问题已分别标识，不把历史曾做过的功能自动视作本次正式范围。
- **S4 → S5**：用户确认本次需求、可观察验收和边界，明确 S1/S2 事实输入版本与未知项。未经确认，不允许冻结 V2 架构。
- **S5 → S6**：可比较的方案与责任边界已评审，用户批准设计；涉及真实模型、Provider、Build、发布或其他付费/不可逆操作另行明确授权。
- **S6 → S7（真实用户阶段验收）**：先使用用户已选定的六维画像、频道和导演真实从Web制作一部可审阅视频，核对所用身份/风格/配置、完整音画产物、Rights/调用/恢复与Creator实际审阅反馈；接受与否必须有明确记录，不能把技术出片当作Creator接受。若有妨碍本次作品可审阅、事实正确、安全合规或用户接受的实证阻断，限范围修复；完成该真实路径后优先提交S6结果与剩余问题清单，由用户决定是否进入S7。未完成的用户接受或语义QC保持真实状态，不借阶段推进补记PASS。

## 全程执行原则

- **历史事实不等于本次需求；历史失败不等于本次修复任务；历史解决方案不等于 V2 必选架构。**
- 旧 `easel-studio` 和私有运行证据始终只读、独立归档，不合并旧协议/Checkpoint/Attempt；新 V2 基于当前官方底座形成自己的正式输入。
- S2 同时关注正确原则、成功资产、已证实缺陷、合法拒绝、设计演进和未验证风险；不围绕 22 个不足只构建负面清单。
- 当次需求未正式确认前，`1～900 秒`、四声音模式、具体模型、固定审核次数等只可作历史或候选事项；真实实施范围必须经 S4 批准。
- 模型、程序与用户的权限分开；真实 Rights、授权、费用、数据保护和 `UNKNOWN` 幂等约束不因追求 PASS 数量而绕过。
- 遵循证据层级：`DESIGNED` / `IMPLEMENTED` / `SOFTWARE_PASS` / `REAL_PRODUCTION_PASS` / `CREATOR_ACCEPTED`。任务未跑写 `NOT_TESTED`，真实阻断写真实原因。
- 不为了补全架构图增加无收益的 Agent、Gate、数据表、长 Task；阶段 S5 的任何技术选择须同时解释需求、现有能力、历史正反证据、成本和替代方案。
- 阶段完成后更新 [当前状态](../../project/status.md) 的唯一下一动作；Roadmap 只在阶段顺序/定义变化时更新。不自动合并 PR、更新官方上游或擅自启动下一阶段。
