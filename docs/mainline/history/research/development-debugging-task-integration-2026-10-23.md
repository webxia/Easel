## 一、已确认的整合目标与关系

**以现有任务体系为载体，统一开发规范、调试规范，以及调试发现 Bug 后如何按开发规范修复。**

不是再建设 AI Coding 平台，也不是为 Codex 增加一个外部调度器。Codex 仍是工程执行者；现有需求、设计、实施任务包、Task、测试和运行记录继续使用。

三者的关系确认为：

- **开发规范是所有代码变更的共同规范**，覆盖需求分析、方案设计、实施、检查、验证与交付。
- **调试规范说明如何验证、观察、取证、定位和判断下一步**，不能成为“调试时可以绕过正常开发”的例外。
- **Bug 修复是开发活动的一种**，复用开发规范；只增加缺陷复现、根因说明、防回归和原场景复验等必要内容，不另建一套修复制度。

任务体系贯穿三者：同一个目标从开发到调试再到修复与验收，始终有明确的 Task 归属。错误不是自动创建新任务的理由，也不是自动请求用户再次说“继续”的理由。

```text
当前已批准 Task
  → 按开发规范实施
  → 按任务验收条件验证／调试
      ├─ 达标：记录证据，按任务范围收口
      ├─ 发现当前 Bug：由现有 Task 承接
      │    → 按开发规范分析、设计、实施、验证
      │    → 回到原失败场景复验
      │    → 继续原 Task 剩余验收
      ├─ 非当前阻断：登记到既有候选池，回到当前任务
      └─ 需求／设计／授权有实质冲突：沟通决定后再处理相关动作
```

以上是一个任务内部的执行过程，不是新的建设阶段、审批层级或产品状态机。
### 1.1 已确认的长期设计原则

1. **一个共同开发规范**：新功能、Bug、调试中的代码修复、回归修复均按问题/需求分析 → 方案设计 → 实施 → 检查验证 → 交付执行，记录深度按风险调整。
2. **一个已有任务体系**：实施任务包管依赖和范围，活动 Task 管目标和结果，E2E 运行记录管首次失败与真实回执，CURRENT_STATE 管唯一当前入口，不建立平行系统。
3. **Codex 原生执行**：继续使用已有文档、代码、测试、CI 和开发工具，不增加外部监督控制器、Agent 群、机器任务协议或额外审批状态机。
4. **原任务验收不断线**：普通 FAIL 不是任务结束；在原授权内按开发规范修好并定向复验后，继续原 Task 剩余验收，不需用户反复传话“继续”。
5. **指令有实质偏差先沟通**：用户可能主动修改目标，AI 应说明旧新差异、影响及推荐，由用户决定，再按实际需要更新原权威文档。
6. **停止以验收和风险为依据**：完成当前授权的目标即收口；不能安全恢复或缺决策时明确阻断；无新证据不反复试错。不以普适“三轮/六轮”限制普通工程修复。

### 1.2 本设计权威如何使用与修订

- **整合设计优先级**：对这项规范整合工作而言，若此前实验性的控制器说明、旧 E2E 操作模板或另一份研究方案与本文冲突，以本文为唯一设计依据；操作仍受当前用户权限、安全与真实代码边界约束。
- **产品要求不被覆盖**：产品行为以用户已确认需求及最新决定为准；长期职责以已接受架构/合同为准；源码、测试和运行回执只证明对应版本的实际行为。
- **新决议直接修本文**：以后用户提出实质性不同方向，先列差异与影响并沟通，确认后修改**本文件**及必要原权威文档，保留 Git 差分；不再复制出“新版整合方案”。
- **批准与落地分层**：先前工程说明、Task 模板和 INDEX 曾引用未获认可的控制器；这解释了为何需要实际迁入。现已按后续授权调整上述**文档入口**（见 §9.4），但真实 Codex 开发→修 Bug→E2E 回接仍须用原任务验收，不能把文档检查称为运行效果 PASS。

**不足不在于“没有这些文件”，而在于边界和衔接仍需统一。** 例如，运行记录说明了哪里失败，但修复归属、方案依据、代码验证和“返回哪个原场景”不应依赖用户在聊天中反复串联；调试中的临时补丁也不应避开既有开发约束。

**信息权威与证据边界**：需求/设计/合同说明“应当怎样”，本次 Task 与用户授权说明“要做到哪里”，实际源码/运行回执说明“当前实际怎样”，调试记录说明“哪次、何版本、哪里失败”，CURRENT_STATE 只保留当前入口及非阻断候选。静态推测不是已发生的 Bug；旧版本 PASS 不是本次 PASS。

**已纠正的历史偏差**：工程说明、Task 模板、E2E README 曾把 `scripts/engineering.py` 与机器契约描述为执行路径；导航一度仅连接设计而未完成实施。后续整合已从**现行文档**中撤出该依赖，统一指向原生 Codex、开发规范和活动 Task。控制器/Schema/模拟测试本身仍是工作区已有的实验性文件，未删除或验证可投入正式使用；模拟测试 PASS 不等于真实协作问题已解决。

## 三、统一开发规范：普通开发与 Bug 修复走同一条链

正式整合时必须将下表关系收敛到**现有**工程说明和任务共同约定，不能再新增一份独立开发手册。

| 同一开发环节 | 普通开发怎样做 | Bug 修复怎样做 |
|---|---|---|
| 需求／问题分析 | 明确用户需要的行为、范围和验收标准 | 对照已有需求说明预期与实际差异，确认问题是否真实存在、是否阻断当前任务 |
| 方案设计 | 说明职责、实现方案、取舍、影响与验证方式 | 根据证据说明根因或待验证假设、必要修复方案、影响范围及如何防回归；沿用原架构和合同 |
| 开发实施 | 在任务与授权内修改实现，保护原有改动 | 按已分析的原因实施修复；不能为消除报错顺带重做无关模块或降低正确性标准 |
| 检查与验证 | 检查 Diff，执行适用测试，确认实际行为符合要求 | 保留失败样例，验证修复前后差异、相关正反例及关联回归；检查是否引入新问题 |
| 场景验收与交付 | 完成当前 Task 声明的验收，记录结果和未覆盖项 | 返回原失败场景定向复验，再完成原 Task 剩余验收；修复单测通过不等于原调试任务完成 |

### 3.1 流程一致，但文档和评审深度按风险调整

**“按开发规范修复”不等于每个小 Bug 都重新写需求文档、设计文档和 Task。**

局部实现错误、原需求与方案均明确时，在当前 Task 的执行记录中补充问题、原因、方案和验证即可。Codex 可以在既有授权内连续完成，不必为每个分析步骤请求批准。

如果修复触及接口行为、数据模型、模块职责、迁移或较大兼容性影响，就按原开发规范补充必要的影响分析和方案复核；涉及已确认设计或需求改变时，先沟通并更新对应权威文档，再实施。单纯跨多个文件不自动意味着要立新项目，改动只有几行也不自动意味着低风险。

选择的是**能正确覆盖根因的必要方案**，不是机械追求最少行数，也不是借“彻底解决”无限扩建。临时绕行须标明限制，不能作为根因已修复的证据。

### 3.2 验证服从任务，不机械扩大

文档修改做适用的文档检查；局部代码修复做针对性正反例和关联回归；影响真实交互或生产路径的修复，在授权内回到相应场景复验。是否需要完整 E2E、固定版本独立验收或人工审片，沿用当前 Task 的完成条件，不因发现一个 Bug 自动扩大到全部功能矩阵。

测试本身也可能有错。可以基于已确认需求修正测试或夹具，并保留修改理由；不能仅为了绿色结果删除断言、增加跳过、放宽合同或把未测写成通过。
### 3.3 Bug 修复遵守同一开发规范，深度由风险决定

| 问题类型 | 必要的分析/设计 | 必须验证什么 | 不得做的事 |
|---|---|---|---|
| 局部实现错误，已有需求和合同清楚 | 在活动 Task 写明预期与实际、具名原因、必要方案和影响；无需重写需求/ADR | 失败复现、正反例、关联回归，以及本次授权范围内原场景复验 | 为绿色结果删除断言或放宽保护 |
| 跨模块但不改变职责/合同 | 核对调用链、消费者输入输出、持久状态与恢复语义，说明跨模块修复的必要性 | 受影响模块的合同和状态不变量、原问题是否消失 | 因涉及文件多就自动另建工程，或顺带重构无关模块 |
| 影响接口行为、数据身份/兼容、状态机职责 | 按既有开发规范先做影响分析与方案复核；若修改已确认设计/需求则向用户沟通 | 幂等、兼容、回退、数据保护与必要真实场景 | 从一次失败直接推导并实施新架构 |
| 外部模型/素材/费用/UNKNOWN 不确定 | 先核实原始响应、Operation、权益、权限和能否合法恢复 | 原操作身份、结果/副作用和负例保护 | 盲重发、换 Provider 绕过错误、改库或伪造业务 PASS |

**根因方案的最低信息**：预期/实际与证据 → 首次失效点 → 已证事实与未证假设 → 责任边界 → 必要修复及取舍 → 影响范围和复验 → 哪些后续优化不属于本轮。小 Bug 可压缩到活动 Task 的几行执行记录，不为满足形式再建文档。


## 四、调试规范：先形成可处理的问题，再进入开发修复

调试的核心是回答四个问题：**本轮在验证什么、哪里与预期不符、证据指向什么、下一步是恢复还是修改。**

开始时沿用当前 Task 的目标、验收条件、授权与已有运行断点，核对受测代码及实际运行版本。保留已有成功结果，不因新会话或新窗口重新定义目标。

出现异常，先记录首次可证实的差异及最短复现线索，再判断原因：可能是实现缺陷，也可能是环境、测试夹具、工具中断、输入约束或需求理解偏差。**看到 FAIL 不等于必须修改产品代码；看到产品拒绝某个操作，也不等于拒绝本身是 Bug。**

能用已有日志、原始响应、单测或局部集成定位的，先使用这些证据。重新向模型发送相同请求是新一次运行，不等于回放上一次失败。涉及在途调用或 UNKNOWN 时，先查原操作结果，不盲目重发。

确认需要修代码后，回到第三节的共同开发流程。修复及关联验证完成，再在合法入口执行原场景复验；只有部署实际需要且已获授权，才核对在途操作并更新服务。软件通过、部署通过、真实场景复验和 Creator 接受分别记录。

**调试跑通与固定版本独立验收继续区分。** 有工程介入的成功如实记录；固定版本验收失败后可以转回调试，但不能覆盖该轮失败，或在改过代码后声称原版本一次通过。

重复失败时应先检查假设是否被证据推翻，补充观测或调整诊断方法。没有新证据就不机械叠加补丁、改 Prompt、重复付费重跑；也不设置“失败一次就找用户”或统一“最多三轮／六轮”的常驻研发门槛。真实费用、调用次数和安全授权仍按原约束执行。
### 4.1 先分类，再决定是否需要修改产品代码

| 首次现象 | 要核实的事实 | 对应动作 |
|---|---|---|
| 浏览器、Codex、Runner、消息回复中断 | 当前浏览器是否还在、原 Work/Run/Operation 是否持续执行、最后一次写入是否产生副作用 | 先按工具/环境恢复，不能凭页面或命令中断重新付费制作 |
| HTTP/SSE 或 MODEL Operation 成功，但 Plan 仍 FAIL | 原始模型输出、冻结上下文、解析/校验合同、受测版本与真实消费者 | 区分模型语义输出、上下文投影、结构合同和代码解析，不因 HTTP200 就改回业务 PASS |
| 素材检索失败或候选不合格 | 检索是否有候选、字节能否获取、Rights、具体用途和质量是否匹配 | 区分无结果与权益/技术拒绝；按实际责任修复，不临时绑定无关素材 |
| 本地渲染失败 | 实际源文件、命令参数、FFmpeg 回执、已成功上游 Task/素材 | 对确定性首因做受控代码修复和复验，不因渲染错误重规划整片 |
| 技术通过、语义失败或 Creator 不接受 | QC 实测覆盖、真实音画、当前版 Plan/作品、用户反馈 | 保留技术 PASS 与语义/接受 FAIL，按授权执行必要局部修订 |
| Provider HTTP500、UNKNOWN、Rights/费用未定 | 原 Operation、是否有已确认回执、正在执行/收费或未知副作用 | 安全保护优先，不盲重试、不改库、不换模型来绕过 |
| 确证代码或测试 Bug，阻断当前 Task | 可复现证据、期望与实际、直接根因、当前任务范围 | 回第三节的共同开发流程：分析、必要方案、修复、回归、原场景复验 |
| 本轮不受阻但发现可能优化 | 具体证据、为何不阻断、是否现有候选 | 归并到 CURRENT_STATE 已有候选池；不顺手开发 |

技术分类沿用 `DEBUG_RECOVERY / ENVIRONMENT / TEST_BUG / PRODUCT_BUG / UNKNOWN`；当前处理优先级沿用 `SAFETY / CURRENT_BLOCKER / LATER / RESEARCH`。这些是原有的两种判断维度，不新增另一套 Task 状态机。

### 4.2 一次完整调试内部的执行纪律

- **首次证据优先**：保存预期/实际、发生时版本与真实加载配置、原始响应或私有证据索引、最近已确认成功节点与首个失败节点；不把恢复成功改写成旧失败没有发生。
- **低副作用复现优先**：利用原回执、日志、离线 Replay、具名测试和已有阶段集成夹具。重新发送同一 Prompt 是新的模型请求，不等于“回放”旧失败。
- **有因果再修代码**：先区分环境、工具、测试和产品缺陷；真正需变更实现时回开发规范，做相关风险分析、必要方案及正反回归。
- **复验从影响点开始**：合法时保留同 Work、同版本已成功 Plan/素材/声音和 Operation，按原入口恢复受影响阶段；如冻结上下文不兼容或需要新作品，明确原因及授权，不能直接手写 SQL 伪造恢复。
- **同一个 Task 继续走完**：当前阻断解除后核对原 E2E/实施 Task 剩余验收，不自动结束，也不因为新发现其他非阻断问题而把范围扩成平台治理。


## 五、完整复用现有任务体系

### 5.1 明确四类信息各归其位

**实施任务包负责依赖与范围，Task 负责工作与结果，运行记录负责现场证据，CURRENT_STATE 负责当前入口。** 它们互相引用，不复制全文，不产生多个“唯一下一步”。

以一次 E2E 失败为例：运行记录保留首次失败及证据引用；活动 Task 的执行记录承接原因、修复方案和验证；任务完成条件决定是否收口；CURRENT_STATE 只在当前任务、阻断或接手位置改变时更新摘要。

本文件讨论的 Task 是**仓库研发任务**，不是 Easel 产品内的 Work、Plan、Run 或生产 task。修改研发记录不修改业务状态；“任务暂停”也不代表外部生产已经取消。

### 5.2 发现 Bug 后，怎样决定任务归属

| 情况 | 使用现有体系的方式 |
|---|---|
| 当前功能开发或验收内的普通 Bug | 默认记入当前活动 Task 的执行记录，沿用其完成条件；不要因每个错误新建 Bug 卡 |
| 当前 E2E 跨多个功能，修复有独立依赖、需要单独安排或明确交接 | 优先关联现有适用的活动任务；确有必要时才使用原 Task 模板建立关联修复项，仍归入原实施任务包，不引入新命名体系 |
| 原实现任务已经关闭，当前验收发现回归 | 原卡作为来源引用，修复由当前活动任务或必要的关联任务承接；不静默重开所有历史卡，不改写旧版本验收事实 |
| 不影响当前目标的缺陷或优化 | 按既有候选池归并记录，说明影响、依据和为何不阻断；不提前实施、不另建 Backlog |

拆分的依据是**是否需要独立交付、依赖和跟踪**，不是错误数量、涉及文件数量或为了显得流程完整。关联修复项即使关闭，父级调试／验收任务仍须完成自己的剩余条件。

### 5.3 现有 Task 字段怎样承接，不新增必填表单

“关联需求／相关设计”引用已有条款；“范围／不做”说明修复边界；“完成条件”指出原问题消失且关键正确行为不退化；“执行记录”承接证据、原因、方案与结果；“未闭合风险和下一动作”指出原场景从何处继续。

这些内容可以压缩在原 Task 的一段记录中，例如：

```text
问题：当前验收场景中的点缀音效超出真实源时长。
依据与原因：链接首次失败记录、相关合同及源时长核对结果。
方案与范围：只调整点缀音效的适配，旁白/BGM和越界保护不变。
验证与结果：具名正反测试、关联回归；原场景是否已复验。
原任务接续：从合法剪辑恢复入口继续；未复验则仍有未完成验收项。
```

这是既有字段的写法示例，不是另一张强制 Bug 模板。沿用既有 Task 结果口径，例如 COMPLETE／PARTIAL／BLOCKED；“等用户决定”写清阻断原因，不额外发明任务状态或自动调度协议。

### 5.4 任务完成不能偷换为局部动作完成

“修复提交完成”“相关单测通过”“后台命令结束”都只能证明对应动作。若当前 Task 目标是验证完整用户场景，Codex 应在已授权且安全的范围继续复验和后续步骤，而不是把下一动作交还用户重新调度。

若本次只授权代码与离线测试，则完成该范围后停止，真实验证保留未测；不能以流程图列出后续步骤为由扩大授权。
### 5.5 中断恢复：任务、代码和业务身份三条线均须核对

跨聊天窗口、Codex 会话或工具中断接手时，利用原 Task 已有的“基线与现场、执行记录、未闭合风险和下一动作”字段，保留最少必要事实：分支/HEAD/Dirty 与实际加载构建；本轮验收对象和剩余 Gate；首次失败与最近成功证据；最后非幂等操作的原始终态及 UNKNOWN；原 Work/Plan/Run 的可恢复入口；唯一下一动作。

- **工程身份**：已有 Dirty、原有未跟踪资料、个人 Profile/outputs、已接受旧作品与历史证据不清理、不覆盖。不能仅凭同一个 HEAD 就假定线上服务和浏览器加载的代码一致。
- **业务身份**：程序 Task 与 Easel 产品内 Work/Plan/Run/Operation 是不同对象。原操作超时或 UNKNOWN 时先查结果与副作用，再决定是否允许任何新写动作；已有成功产物应合法复用。
- **责任归还**：必要关联 Bug Task 关闭后，原父 Task 的 E2E 结果与剩余验收仍然有效，不将“子问题通过”升级为整项任务 COMPLETE。
- **自动继续的限度**：Codex 在当前实际授权的会话内有合法下一动作则继续；若工具会话确实结束，靠现有任务与运行记录恢复。文档规则不承诺没有实际运行进程的后台无人值守。


## 六、用户指令有偏差时如何沟通

用户的新要求可能是表达不清，也可能是主动改变目标，不能一概判断为“用户错了”。Codex 应核对事实并说明冲突，而不是盲从，也不是拿旧文档否决用户的新决定。

当新指令与已确认需求、设计或当前授权有实质差异，先说明：**具体指令与哪条决定不同、直接执行的影响、建议保留原目标还是变更目标、需要用户确认哪一点。** 暂停有争议的写入，保留安全且不依赖该决定的只读工作。

例如，用户提出“先把失败检查关掉让流程通过”，如果该检查保护源文件有效性，就应说明关掉后可能产生无效成片，推荐修复源长适配；若用户实际是希望省略一个可选音效，则这是交付范围决定，应按确认后的范围处理，而不是伪造该音效已完成。

用户明确确认后，将决议记入原 Task，并且**仅在需求或设计真的改变时**更新相应权威文档。普通实现修复不改写需求。已有明确授权持续有效，同一范围内的诊断、实现、测试不反复请求批准。

日常应减少的是人工传话、重复“继续”和反复解释上下文；不应消除需求取舍、权限、费用或 Creator 审片等真正需要人的决定。会话或工具确实中断时保存现有断点，恢复后核对事实继续；文本规则不能承诺会话结束后自动后台运行。
### 6.1 只在实质偏差时采用的一次沟通格式

沟通必须能回答：**用户此次指令/操作是什么、与哪条已确认决定不同、直接照做有什么影响、可选方案及推荐、需要用户确认的唯一问题**。用户新要求可能是合法调整，不得简单用旧规范驳回；用户确认后把决议写入原活动 Task，仅当产品需求或设计真的改变时才修改相应权威文件。普通同范围修复不反复要求批准。

例如“关掉源长检查先出片”：如果该检查保护素材有效性，应说明关闭全局校验的风险，推荐对点缀 SFX 按真实源长适配；若用户决定省略普通动作音效，这是产品交付取舍，按明确授权登记降级，不得声称该声效已实际混入成片。

### 7.2 这些经验要求我们停止哪些调试方式？

**错误方式**：一个 Planning FAIL 就重写整套 Prompt/审核规则；看到 HTTP 200 就认为合同合法；某个素材文件存在就认定 Rights/用途正确；渲染一失败就重新规划/配音/收费；因为 Browser 丢失就重建作品；把真实语义 FAIL 记成“技术已 PASS”；为了降低人工接管次数，把所有问题都交给外部控制器循环。

**正确方式**：保存首次失败 → 确定需求与实际差异 → 分类归因并找到首因 → 由当前 Task 按开发规范选择必要方案 → 补对应正反例/回归 → 确认受测源码与真实部署版本 → 在授权范围恢复原业务 → 返回父 Task 剩余验收并如实收口。修复一处旧坑要留下可复用的测试与证据，而不是积累另一组永久 Prompt 或 Task 编号。

6. **用真实任务验收规范**：选择原本已经授权的正常任务，在 Codex 实际执行中核对是否完成“分析→必要方案→修复→关联回归→合法原场景复验→原 Task 收口”，而不是再建一个完整媒体作品作为演示。缺真实调用授权就按软件/离线范围如实收口。
