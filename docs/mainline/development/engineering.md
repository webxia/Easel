# 统一开发规范

状态：**CURRENT — 研发操作入口**。遵守 [仓库根开发规则](../../../AGENTS.md)；原生官方行为以当前版本代码和 [CONTRIBUTING](../../../CONTRIBUTING.md) 为准。

## 1. Agent 角色与指令加载

- **研发 Agent**：修改仓库、测试、设计；短入口是根 `AGENTS.md`，按 [INDEX](../INDEX.md) 阅读相关上下文。
- **产品创作 Agent**：使用 Easel 执行用户创作；其规则源是 [创作 AGENTS](../../../agents/workspace/AGENTS.md) 和按需 Skill，不应加载研发执行任务清单来代替业务指令。
- 官方 [Agent Harness 文档](../../agent-harnesses.md) 说明产品 Agent 可在 Easel 根目录启动，且原生底座有不同指令加载机制。因此 **分文件不等于已隔离**；后续必须实际检验 Codex/OpenClaw/其他底座加载内容。不得在未经验证时自动声明隔离生效。
- 依赖工具、版本和配置的 `AGENTS.md` / `CLAUDE.md` 发现行为需要按实际使用的底座验证。仅因准备兼容某工具，不复制出多套可独立演化的长期规则。
- 六维画像继续使用既有 Profile，不另建主人设体系。依赖安装、运行和真实调用按具体 Task 与当前用户授权执行；文档检查不触发付费会话。现有实施记录见[实施任务包](../project/tasks/S6_IMPLEMENTATION_PLAN.md)。

## 2. 接手任务与交接

接手与收口按[任务衔接清单](task-handoff.md)核对目标、授权、依赖、HEAD/Dirty、验收与剩余事项。小改动可只在PR记录；跨会话/跨模块使用[Task模板](templates/TASK.md)，重大长期决策才使用[ADR模板](templates/ADR.md)。具体开发流程及任务归属如下。

### 2.1 统一开发规范：新功能与 Bug 修复遵循同一流程

**已确认需求／具名问题 → 问题分析 → 方案设计及影响评估 → 开发实施 → 检查验证 → 原 Task 验收／交付**。新功能、维护、调试中发现的 Bug 和回归修复均遵守这一流程；流程一致不代表小 Bug 必须重写需求、设计文档或新建任务卡。

1. **分析**：读取当次用户指令、当前 Task、已确认需求、架构／实施合同和实际失败证据；明确期望与实际、首个可证明的失效点、责任范围，区分已证事实与待验证假设。
2. **方案设计**：描述能覆盖根因的必要方案、职责及接口影响、取舍与验证方式。局部问题在原 Task 简要记录；跨模块问题核对调用链、持久身份与恢复；若需要改变冻结需求、职责或合同，按 §2.3 先与用户沟通。
3. **实施**：在原目标与授权内修复。正确解决问题允许必要的跨文件或结构性调整，但不顺带做无关优化、新增审核 Agent／Gate 或升级到未来阶段。保护既有 Dirty、Profile、Outputs、已接受作品、资产及 UNKNOWN。
4. **检查与验证**：检查 Diff，执行关联正反例、离线回放和受影响回归；影响较大时扩大测试范围。测试夹具有误可按需求修正并注明理由，不以删断言、增加 skip、放宽状态／Rights 保护取得 PASS。
5. **回接与交付**：修复阻断后回到原失败场景，按当次授权完成原 Task 的**剩余验收**；软件 PASS、工具执行结束或子 Bug 修复不自动关闭父 Task。仅授权离线实施时在此收口，真实 E2E 保留 NOT_TESTED。

**分析和评审深度按风险调整，不以改动文件数或行数判断。** E2E 的 G0～G6、工具与业务恢复、真实操作副作用和固定版本验收只在[调试/E2E 规范](testing.md)维护；已批准的整合设计依据见[历史设计依据](../history/research/development-debugging-task-integration-2026-10-23.md)。

### 2.2 复用现有 Task：调试发现 Bug 后回到开发规范

- **当前 Task 内阻断**：E2E/调试轮次保留首次失败、实际版本和私有原始回执；活动 Task 用已有“关联需求／相关设计、执行记录、完成条件、结果、未闭合风险和下一动作”承接根因、方案、代码与测试；按 §2.1 修复，再返回原场景和父 Task 余下验收。不因每次报错新建 Bug 卡，不让用户负责反复转述“继续”。
- **必要独立修复**：确有独立依赖、交付和跨任务交接需要时，先关联已有负责卡；仍有必要才使用[原 Task 模板](templates/TASK.md)建关联项。子项完成不意味着父 Task 完成，旧轮 FAIL 不得覆盖。
- **已结案任务回归**：保留历史卡和当时判定，由当期活动 Task 或必要关联项承接新问题，不批量重开旧阶段。
- **非当期阻断**：具名证据及不阻断理由归并至[既有候选池](../project/backlog.md#s7-candidates)，不另建平行 Backlog/Issue、自动扩大目标；未证实假设标为待验证。
- **信息权威各归其位**：需求和合同定义预期；任务包记录依赖与覆盖；Task 负责目标、方案、验证与结果；E2E 轮次记录首次故障和实际运行；CURRENT_STATE 仅汇总当前入口。仓库 Task 不等于产品内 Work/Plan/Run/Operation，文档变更不能代替业务状态写入。

### 2.3 指令偏差先沟通；按任务授权连续执行并收口

用户新指令可能是合法的方向调整。若与已确认需求、架构职责或授权**实质冲突**，先列出旧决定及出处、这次差异、直接执行的影响、可选方案和推荐，提出一个明确的决策问题；暂停有争议的写操作，保留安全的只读调查。确认后在原 Task 记录用户决定，仅当需求或设计真正改变时才更新相应权威文档。普通同范围分析、编辑、测试与必要修复无需逐步重复授权。

同一合法目标内有新证据和明确下一步，Codex 在当前会话及权限下继续定位、修复、回归、合法复验；相同失败反复出现而无新证据时停止盲目补丁、先核对假设和缺失证据，不能安全推进则报告 BLOCKED。**不设普通研发的统一固定修复轮数**；真实费用、外部非幂等操作、UNKNOWN 和产品自动修订策略继续由原授权与合同严格控制。

工具会话结束不等于 Easel 产品 Work 完成；跨窗口先核对 Task 的 HEAD/Dirty、实际部署、运行记录、原 Operation 与副作用，不承诺不存在的后台自动执行器。以既有 COMPLETE/PARTIAL/BLOCKED 表述任务，以 SOFTWARE_PASS、REAL_PRODUCTION_PASS、CREATOR_ACCEPTED 分列验收，不能让局部成功冒充原目标成功。

## 3. 官方已有工程入口（在对应场景使用）

本节汇总当前仓库入口，其中包含二开新增检查，不表示全部为官方原生工具。

从仓库根目录、项目 Python 环境执行，验证过程默认不触发真实外部调用：

| 检查范围 | 已有执行入口 |
|---|---|
| 技能结构/契约 | `python scripts/validate_skills.py` |
| SKILL 文档命令 | `python scripts/validate_skill_commands.py` |
| Markdown 链接与路径 | `python scripts/validate_document_paths.py` |
| Python/技能自动化测试（发现所有目录） | `python -m pytest` |
| 前端 lint、构建 | 在 `web/frontend` 下执行 `npm run lint`、`npm run build` |
| 安装与启动环境 | 官方 `README.md`；安装检查用 `easel doctor` |
| 正式 CI | `.github/workflows/ci.yml`，按受影响模块与事件运行 |

按变更类型选必要检查，不为了小文档修改默认跑全部媒体/浏览器测试。离线检查通过不表示实际 Web 对话、Provider、Build 或 Creator 审片通过。测试环境应隔离真实配置，不能为了让 fixture 通过清除用户已有 Key/素材。

## 4. 工程规则怎样具有执行约束

- 能机器判断的结构、类型、路径、链接、测试由脚本/CI承担；会修改文件/启动进程/远端操作的权限由实际工具与运行环境控制。
- 根指令不是强制安全门禁。真实发布、不可逆外部动作与费用仍以运行时可执行授权为准。
- CI 在本地修改不能证明远端 Workflow 已运行。只有推送后形成具名结果才能记录为 CI PASS；合并所需 status checks 是否强制需另核实平台设置。
- 已存在的 CI 直接 push 主线应包含 `easel-v2-rebuild`；Pull Request 仍保留。贡献指南的本地 pytest 发现范围与 CI 保持一致。

## 5. 三类验收与优化口径

| 等级 | 证据边界 |
|---|---|
| SOFTWARE_PASS | 在具名 Git/工作区版本上，实际执行对应离线单测、编译、静态/集成验证 |
| REAL_PRODUCTION_PASS | 从合法 Web 确认走真实模型、素材、制作至可播放 MP4，并有产物/来源/费用/恢复证据 |
| CREATOR_ACCEPTED | 有 Creator 对具体输出版本明确接受的记录；仅审阅或提出修改不算接受 |

优化在开始前先定义比较样本和可测量分母；**现在不捏造目标值**：

- 模型调用量：按作品统计真实 Provider 请求，区分常规调用、技术重试、语义修订；记录输入/输出 Token 和实际账单或套餐消耗，不以模型报告 Token 充当现金。
- 时间：从已确认生产请求到可审阅首版，分别记各阶段耗时；排除规则需预先说明。
- 质量/接受率：以事先登记的完整作品样本为分母，分别记录成功生成、合法阻断、Creator 接受和人工干预；不得事后删失败作品。
- 恢复：区分同一外部 Operation 的观察/复用、局部重新调用与重复副作用；UNKNOWN 只能按原身份核验，不盲重派。
- 只有在业务安全/内容义务不下降的条件下，调用量、耗时或恢复性改善才算有效优化。

## 6. Git Fork、官方同步与成果推送（已确认工作规范）

仓库关系：`ZJU-REAL/Easel`（`upstream`）→ `webxia/Easel`（`origin`）→ 本地。`main` 跟踪官方 `upstream/main`，仅承接官方镜像；`easel-v2-rebuild` 是二开长期主线；`easel-studio` 为封存历史，不自动迁入。复杂或高风险工作可使用 `feat/*`、`fix/*` 或 worktree；小改动不强制建分支。

### 6.1 官方更新：每周检查 + 新阶段开始前检查

- 每周一次检查上游更新；在**新阶段开始前**再次检查。检查是触发条件，不意味着自动执行定时 Git 命令；只有实际启动的任务/明确授权的调度才会执行。
- 检查流程：确认当前分支、HEAD、工作区和任务是否运行 → `git fetch upstream` → 比较官方新提交、变更文件与 V2 当前需求/接口 → 输出影响、冲突与推荐同步窗口。检查过程不改变 V2 HEAD。
- 正在开发/验证的任务不中途静默换基线；安全修复可立即评估，但**任何官方变更合并进入 `easel-v2-rebuild` 前，必须先报告差异并取得用户明确确认**。低风险、CI 通过、没有冲突都不能代替该确认。
- 获准后，在干净或安全隔离的工作区同步；先评估 `origin/main` 是否能安全快进至 `upstream/main`，再以可审查的普通 merge 更新 V2；出现冲突必须人工审查语义，不能机械选择 ours/theirs。运行受影响的测试并记录新的上游/V2 SHA 与回归状态；失败则保留旧有效基线和证据，不强推、不隐瞒。

### 6.2 自有开发成果：任务完成自动提交与推送

- **用户已批准的研发任务**满足对应验收条件后，允许 Codex/开发 Agent **自动 Commit + Push 到自己的非保护开发分支**（例如 `feat/*`、`fix/*`），不用每次重复询问；仅适用于用户已批准的工作范围，不能因此开启新任务或扩大到业务生产/付费操作。
- 提交前必须检查目标分支及远端跟踪、`git status`/diff、实际验收与凭证/敏感文件、原有未跟踪数据；只显式暂存本任务修改，不能无差别 `git add -A`。提交说明关联任务或需求，Push 后核实远端 SHA 与 CI；若远端失败或含冲突，报告失败而不是宣称完成。
- **`main` 和长期 `easel-v2-rebuild` 按受保护主线处理**：完成的短期分支通过受控 PR/合并进入 V2，必要测试和审查完成后才发布主线版本。未完成任务跨天/跨窗口可在自己的 WIP 工作分支提交检查点并推送，但不得将其标记为验收通过或直接合并到 V2。
- 若用户仅授权“改文档/代码、不提交或推送”，该次更具体的限制优先；未明确允许的远端覆盖、GitHub Release、外部发布仍需单独授权。不能把这一条当作对任意 Git 写操作的总授权。

### 6.3 里程碑与禁止动作

- 重要里程碑验收后固定 Git SHA、测试/质量证据及必要的版本标记；标签和向长期主线合并须符合当前授权，不自动发布 Release。
- 禁止在共享分支自动 `push --force`、`reset --hard`、清理已有未跟踪文件、改写公共历史，或使用未审查的合并冲突选择。代码回退与数据回退分别评估。

## 7. 反馈沉淀，防止骨架膨胀

| 实际反馈 | 维护位置 |
|---|---|
| 产品行为变化 | 需求及对应验收 |
| 模块责任、长期方案变更 | 架构/必要 ADR |
| 局部缺陷 | 对应测试、Task/PR |
| 可重复的工程执行失误 | 本文件或自动化校验；只有长期通用规则进入根 `AGENTS.md` |
| 一次性运行异常 | 任务/运行证据，不升格为永久指令 |
| 当前版本实际进展 | `CURRENT_STATE` 更新当前快照；Roadmap 不重复写每日日志 |

不得因为一次故障无止境增加 Prompt、Agent、Gate、文档或测试数量；增加治理机制必须证明其解决已确认的业务风险。

任务具体交接与回退检查见[任务衔接规范](task-handoff.md)；工程规则在本页维护，调试特殊规则在[E2E 规范](testing.md)维护。
