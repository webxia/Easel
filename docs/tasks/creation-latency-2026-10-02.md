## 2. 并行与汇合顺序

1. **可并行：** BGM 能力实验/最小修复，与视频流程的源码核对/软件优化。各用独立 worktree，从共同 `easel-studio` 基线出发，登记实际 HEAD 和必要未提交输入快照，保护主工作区现有用户改动。
2. **单一运行 Owner：** 原作品恢复、服务加载、实际预算/运行记录由 BGM 目标负责。另一窗口只交付独立软件分支，不运行原作品或加载服务。
3. **整合：** 共同文件的局部修改按两边 Diff 合并，保留双方身份/费用/恢复约束并完成必要组合回归。主工作区 Current State 与本总顺序由 BGM 目标 Owner 统一更新；不互相覆盖。
4. **后续真实 G3：** 原作品正式 MATERIAL_READY 与软件整合完成后，再独立启动固定预期的真实语义案例、Authoring、Build 和 Quality。可播放 MP4、文字/声音/必要表达完整且实际感知核验通过，才认领首版。
5. **后续 G4：** 三个预先固定的新 Content 按各自授权从正常确认开始；均无工程救场完成、无关键质量缺陷，才称该窄路线初步重复验证。同根因两次修复仍失败按 AGENTS.md 复核，失败不无限现场补丁。

原预算不转授新作品，历史诊断作品不倒算自主成功；当前声音失败不改变 required、Rights、Match 或 Readiness。真实恢复/成片的具名证据以 Current State 与 Acceptance 路由为准。

原 G0–G2 的 3.5–8 小时估计已遇能力门失败，不能再当确定剩余工期；新的声音路径明确后重新估计。视频软件目标启动时依据当前真实缺口给出工作量，原 G3 的 2–4 小时包含真实首版，不能直接作为该软件目标承诺。G4 原 2–6 小时仍为后置初步估计。

## 4. 代码借用、回退与路线决策

具体外部源码、固定提交及采用/排除依据见[已完成的 GitHub 调研](creation-latency-completed-2026-10-05.md#132-github-证据与选型结果)。实施时按以下规则选择和移植。

用户已允许移植代码，不因“移植”本身新增确认步骤。选择顺序是：复用 Easel 已有实现 → 采用外部反例/算法思路 → 移植确有缺口的纯函数/小组件 → 经实验必要时才增加依赖。复制时记录仓库/commit/文件/改动与许可证，保留相应版权和 NOTICE；OpenMontage 的 AGPL 代码如纳入交付，须落实适用源码提供/许可义务，不能仍把复制部分标成纯 Apache。此处是移植交付条件，不是要求用户再次同意移植。模型和样本授权分别登记。

当前计划**不新增运行时依赖**：AST 已有；Silero 阈值扫描方法可按本项目分数/指标重写，Ina 只在 G0 失败后成为待评估候选；Instructor/Temporal 参考错误/恢复合同即可；OpenMontage 先吸收选材与职责表达，UI 代码不进入 BGM 批次。真正复制外部实现前比较与现有代码的重叠，避免把第二套 schema、费用或 checkpoint 搬进来。

回退单位是已验证的 policy/协议版本和相应代码，不回退/删除 Creation、原媒体、原始报告、费用账本或失败历史。实验失败不影响生产规则；部署失败恢复原版本，旧结果仅在原身份和适用范围下有效。坏规则已产生的派生通过应保留审计但停止认领，不能靠回退界面隐藏。

三种路线的最终判断依据：若 G0/G1 收敛且 G3/G4 能自主交付，继续 Easel；若素材能力可过但执行/报告边界持续失败，先评估局部替换执行适配器，保持 Domain/账本/主链，另行前置复核；只有同一 brief、预算、人工参与标准下的隔离 OpenMontage 对照真实证明明显优势，且产品化/许可迁移成本可接受，才提出整体迁移。当前未跑此对照，不给迁移工期或成功率承诺。不得因为已有投入而无限修补，也不得因为对方演示成片而推定更适合自主产品。
