# Easel 视频创作架构与技术选型
## V1 经验、V2 需求与开源实践的独立支线研究

版本：1.1　｜　研究日期：2026-10-17　｜　增补：动态规则 Agent 案例　｜　状态：研究建议，未批准实施

> 本文独立于 Easel 主线。它不是新的需求基线、ADR、实施任务或验收结论，不修改主线代码、配置、任务索引及排程。全文中的候选结构、试验和技术选择均须另行评审；本文没有启动真实模型、素材生成、Hypit 运行或生产试验。

## 结论摘要

**建议的目标不是“继续堆叠严格流水线”，也不是“把一切搬给通用 Agent”，而是：Easel 保有业务控制权，创作 Agent 在明确委托内使用技能和工具完成观察、创作、试编排与修正，制作后端保留原生表达能力。**

这一区分比“FFmpeg 还是 Hypit”更重要。V1 的失败包含上下文投影遗漏、创意要求被错误硬化、模型回抄程序字段、技术恢复与语义修订混用等问题；这些问题不会因更换渲染器自动消失。与此同时，V2 目前的部分创作节点仍主要是一次性结构化结果请求，尚未充分利用已经具备的受控工具循环。两者分别提示我们：既不能失去程序边界，也不能把 AI 的创作空间压缩成填写大表格。[V1-01][V1-02][C01][C02]

**对 Hypit 的建议：保留为有竞争力的候选，分能力验证，不整包迁回 V1，也不提前判定不采用。** 其参考分析方法和语义时间编排值得研究；其原生制作能力应与 Remotion、当前 FFmpeg 后端用相同资产和目标效果比较。当前 FFmpeg 可继续作为已实现的运行基线，但不能因此成为所有未来导演风格的上限。[V1-03][V1-04][O01][O02][C04]

| 选型层次 | 本文建议 | 尚未证明的部分 |
|---|---|---|
| 产品与业务控制 | 保留 Creator / Director / Work 关系及 V2 的状态、版本、权限、操作回执 | 当前软件基础不等于真实自主生产已通过 |
| 创作执行 | 优先研究现有受控工具循环与按任务加载的创作技能；必要时再比较外部 Agent Harness | 相比一次性调用的质量、成本和恢复收益 |
| Director 表达 | 风格说明、参考证据、代表试片，加少量必要的执行约束与适配边界 | 不先冻结大型“导演 DSL” |
| 参考分析 | 原生视频理解与专项工具结合，按问题精查，而非只提高均匀抽帧数量 | 同样本下哪种组合最合适 |
| 编辑制作 | 当前 FFmpeg 保留；Hypit / Remotion 按关键风格能力竞争 | 原生工程接入、隔离、局部修订与实际质量 |
| 验收 | 同版本、跨内容、重复运行，分别统计自主、质量、风格和用户接受 | 没有用单条展示样片证明长期稳定 |

**执行次序的研究建议：主线真实闭环与支线关键能力验证可以各自推进；不把完整重构变成首片前置，也不要求等到首片成功后才研究已知的表达缺口。** 本文不改变当前 S6-14 的授权与执行安排。[S01]

## 1. 研究问题与证据边界

### 1.1 我们真正要解决的问题

目标不是生成一个 MP4，也不是复刻某条参考视频，而是：**同一个真实创作者，使用经过确认的导演风格，围绕不同内容，在正常产品交互下持续得到可接受作品。** 这里包含创作内容的变化、表现原则的稳定、制作过程的可靠以及用户对具体作品的接受，缺一不可。[R01]

“无需研发人员介入”不等于用户不能确认方案、补充个人事实、追加授权或审阅作品。它排除的是制作过程中由研发人员改代码、手改数据库、补内部状态、手动替换资产救场，却仍把结果记为自主完成。由产品内 Agent 在授权沙箱中生成某部作品的 SVML、TSX 或其他原生制作文件，原则上可以属于自动创作；它与修改 Easel 业务代码是两种行为，必须通过工具范围和文件边界区分。这是本文提出的职责解释，尚不是已实现能力。

## 2. 从 V1 应当继承什么、停止继承什么

### 2.1 V1 不是“全部失败”，Hypit 也不是已证明的根因

历史上已有可接受成片与有效子链：9 月 30 日的一条 36 秒音画作品得到 Creator 接受，但同一记录明确自主项失败、风格一致性部分通过；10 月 12 日 U3-S 在固定外部回执条件下完成 50 秒本地 Hypit 制作和冷恢复。后期 R09–R19 的多次失败停在 Planning，并没有进入完整真实素材、制作和审阅链。[V1-01]

因此，合理结论是：**V1 的部分制作能力有效，完整产品闭环和稳定风格没有被证明；大量后期失败不能归咎于没有实际执行到的渲染器。** 反过来，本地 Hypit 成功也不能证明采用 Hypit 就能解决整条链。

### 2.2 失败机制对本次设计的约束

| 历史事实与机制 | 本次应保留的认识 | 不应再次采用的做法 |
|---|---|---|
| 确认备注已保存，但 B 审查投影漏掉素材替代许可 | 按消费者核对完整委托，包括允许怎么调整 | 用“冻结成功、哈希正确”代替语义完整性 |
| 7 个镜头按文本非空行展开为 11 个范围，叠加多批审查 | 身份对应业务对象，检查对应真实风险 | 按排版行数建立镜头身份，机械展开每条描述 |
| 浅景深、傍晚光线等被升级为原素材硬条件 | 区分用户要求、导演核心、偏好和后期实现 | 每个创作形容词都生成一个阻断 Gate |
| 模型回抄已知身份、来源字段；合法分批结果仍可能在程序合并失败 | 程序绑定已有事实，模型返回新的创作决定 | 要模型重复生成整套身份和异构传输结构 |
| 格式、工具终态、语义修订共用修复机会 | 分类记录错误，按原因修复，复用有效成果 | 技术故障消耗创作修订预算，再把结果记为创作失败 |
| 搜到候选不等于可下载、许可完整、听感合格 | 获取、权益、用途适配和审美分别有证据 | 以 HTTP 成功、分类器分数或文件名代替实际合格 |
| 软件 PASS、局部真实成功和用户接受发生在不同边界 | 每条验收绑定版本、输入、产物与介入记录 | 把不同日期的成功片段拼成整体自主 PASS |

以上机制来自 S2 C01～C09 和 S3 L12～L20。报告还保留重要的不确定性：通用上下文污染已发现，但它是否导致全部“零工具参数”尚未证实；审核数量多并不证明每项都无用；R19 总调用准入确实挡住了超限调用，不能编造额外付费或现金超支。[V1-01][V1-02]

### 2.3 保留的是产品原则，不是旧协议名字

应继承 Creator / Content / Director 分离、参考不转移个人经历、明确确认与具体版本接受、合法素材复用、原操作身份恢复、声音和文字局部保护，以及真实 Rights / Truth / 授权约束。它们都有清晰产品价值或历史局部证据。[V1-01][V1-02]

不整体继承旧 Proposal / Attempt / Delivery 执行链、A/B/Truth 的固定展开方式、旧报价模型、临时 HTTP 次数上限、按排版构造来源身份，以及与特定 Hypit 内部源码绑定的解析层。旧 `native_source.py` 确实固定了大量内部文件摘要和 darwin-arm64 组件；这提示应固定公共包版本和受支持接口，而不是搬回整个内部兼容面。版本固定本身并非错误，问题在耦合层次与维护范围。[V1-03][V1-04]

### 2.4 U7 应转化为研究方法，而不是另一套任务

U7 的历史状态是未启动的优化 backlog。其有价值的部分是：同版本记录交互轮次、调用和 Token、有效素材率、编排与渲染耗时、局部修改影响、人工介入与最终质量；比较推理档位或缓存时控制其他变量。本文继承这一测量方法，不把 U7 写成已验证优化成果，也不恢复旧任务编号或临时阈值。[V1-02]

## 3. 已确认需求怎样约束选型

| 已确认要求 | 对设计的直接约束 | 不能用什么替代 |
|---|---|---|
| 人设一致、内容变化、导演跨题材复用 | 身份与事实独立，风格可版本化，具体故事重新创作 | 固定脚本模板或复制参考人物经历 |
| 参考拆解 → 风格确认 → 试片 → 接受 | 参考有时间证据；草稿与已接受导演分开；首版可兼作试片 | 保存一段风格文本就宣称导演已验证 |
| 确认后尽可能自主完成 | 执行器能持续工作并处理授权内局部修正 | 一次 LLM 返回失败就必然让用户处理技术问题 |
| 固定音色、字幕和原声保护 | 单片明确值、长期默认及导演建议有优先级 | 参考风格自动覆盖用户固定设置 |
| 必用、历史复用、外部补料、AI 补料 | 候选与实际选中分开；来源、权限和用途可追溯 | 有 Key 就调用，或为了凑素材强行换创意 |
| 局部修订与旧版保留 | 工程、语义事件和媒体有可追踪依赖 | 重做全片、覆盖旧接受版本、只比较文件差异 |
| 四声音、两画幅、1～900 秒及三类输入 | 能力矩阵按实际组合验证；短样片只是试验切片 | 把首条简单视频当作完整范围验收 |
| 可观察、可恢复、UNKNOWN 不重发 | 唯一业务记录与受控副作用接口 | 通用 Agent 的聊天记忆或引擎日志充当业务权威 |

这些是正式需求的约束，不是本报告新加的需求。[R01] 自主创作与安全执行并不冲突：应减少无意义的逐步确认，但不能删除真实事实缺口、权益不足、扩大制作范围时所需的用户决定。

目前首期仍是本机 Web 视频创作，不应为了未来可能的 SaaS、多用户、运营或自动发布，提前扩张成大型平台。商业化许可证风险需要记录，但也不能以尚未发生的部署形态阻断当前已允许的个人使用研究。[R01][O03]

## 4. V2 当前设计：有效基础与关键缺口

### 4.1 已经存在、应该保留的基础

V2 已将作品命令、版本、授权、持久任务、外部操作、素材引用和用户接受分别保存；`TaskContext` 把冻结画像与导演风格传给创作任务；素材层已有持久化意图和用途绑定；编辑前、选中后及渲染前有资产再校验；审片使用实际视频分段并保留局限，不能被全片总结抹掉。[R02][C01～C05]

这说明不需要因为创作表现不足就推翻 SQLite、OperationService、持久 worker 或整个素材库。问题主要应沿“输入证据 → 创作决策 → 执行表达 → 验证反馈”检查，而不是按框架名称找替罪者。

### 4.2 关键发现：具备工具循环，不等于创作环节在使用它

`ModelTaskRunner.run()` 已支持有界工具调用和结构化结果接收；Planning 的方案调用传入工具集合。但是 `analyze_director()` 和 `CreationTasks.edit()` 在当前调用点没有传入工具集合：前者收到预先准备的参考媒体后返回分析，后者收到候选观察后返回完整剪辑结果。对这两个调用而言，模型无法自行发起进一步复看、局部预览或编辑检查。[C01][C02]

**推断：与成熟创作过程相比，当前缺的可能不只是“更多字段”，而是“发现不确定性后继续观察，试做后根据反馈修正”的受控能力。** 这不等于要求无限循环或任意 shell；也不意味着全部失败都能由工具循环解决。它提供了一个比全面换框架更具体的试验方向。

| 位置 | 当前实现事实 | 研究判断 |
|---|---|---|
| `inspection.py:17–70` | 导演参考默认最多 12 帧，音频分块覆盖；不是镜头级自适应观察 | 快速变化、转场过程和字幕动态可能遗漏，需按问题精查 |
| `planning.py:135–185` | 八类自然语言字段保存风格，独立参考证据保存媒体身份与采样 | 可解释摘要有价值，但缺少每项关键判断对应的时间依据与适用范围 |
| `model_tasks.py:91–151` | 已有工具循环、能力检查、有限格式纠正 | 优先验证给现有创作节点开放受控工具，而非先换 Agent 平台 |
| `creation.py:55–84` | 候选视频最多 4 帧观察后一次请求完整剪辑；检查在结果后执行 | 可尝试小范围编排、检查、预览、修正；避免同时塞入全部候选媒体 |
| `material_intent.py:22–60` | SFX 使用绝对 `at/duration`；检查已知场景和全片时间范围 | 数字合法不代表与实际旁白词语或最终镜头事件同步 |
| `editors/base.py:45–164` | 受限场景、音轨、字幕时间线；当前工程类型固定 FFmpeg | 能完成所声明能力，但不能把此类型当所有未来引擎的共同上限 |
| `quality.py:23–79` | 实际视频分段审核并综合，保留失败和局限 | 需增加关键风格依据与实际结果的对应，但不必每条偏好另开审核 |

表中事实为静态源码观察；质量提升、延迟下降和实际失败概率均未实测。[C01～C05]

### 4.3 一个值得优先验证的音画顺序风险

素材阶段已经给出声效的绝对时间，随后编辑阶段才准备旁白资产并获得实际时长；编辑还要求保留声效绑定的 `at/duration`。这一顺序可能出现“按原数值正确放置，但没有跟随实际发音、停顿或镜头揭示”的情况。[C02][C03]

**建议**：素材阶段先表达“某个语义事件需要什么声音”，编辑阶段依据实际音频对齐、素材片段和最终镜头安排，解析成精确时间。已有明确绝对时点应保留；语义事件不应被误认为绝对时点。最终执行时刻仍写入既有编辑产物，不创建第二份可独立确认的方案。

这是由调用顺序推导出的风险，不是本轮发现了一条实际音画错位样片。是否改公共合同、内部投影还是编辑适配器，需要实验后再决定。

### 4.4 不能用需求描述替代模型实际能力

当前状态记录的文本模型配置、素材 Provider 和声音服务，并不自动满足参考视频分析、带音轨完整审片所需的多模态能力。当前代码也有明确的视频协议与能力检查。给文本模型增加“请观看视频”的提示词，或者仅更换模型名称配置，都不构成能力接通。[S01][C05]

因此，选型应同时检查模型能力、传输协议、媒体输入形式、结构化输出、工具调用以及真实授权。先定位缺的是哪一层，再决定换模型、补协议还是改工作流。

## 5. 开源项目给我们的可复用经验

### 5.1 不按“项目热度”选，而按责任层选择

| Hypit | 参考视频细读、局部密集观察、语义时间映射与原生制作表达 | 观察方法、时间关系、组件化编排 | 原生工具存在不代表自动提炼完整 Director；不接管 Easel 授权与作品状态 |
| OpenMontage | Agent 读取 YAML 阶段和 Markdown 技能，调用工具并写检查点；有风格 playbook | 程序性创作知识、工具反馈、过程可观察 | 其 Agent 控制平面不直接替代 Easel 业务控制；不照搬所有人工门禁 |
| Agentic Video Editor | 参考镜头统计进入风格参数，影响候选与剪辑决策 | 可测量特征参与创作，区分语义匹配与节奏偏好 | 小型示例不是成熟度证明；统计量不能代表完整导演风格 |
| MoneyPrinterTurbo | 主题、文案、素材、配音、字幕和合成的自动流程 | 简单成片基线与模块化工具链 | 模板化出片不能直接证明跨题材导演能力 |
| PySceneDetect / WhisperX | 镜头变化候选与语音词级对齐 | 给模型提供时间证据，减少凭空猜时刻 | 检测、对齐结果不是无误真值，需处理中文、音乐与快速运镜 |
| Remotion | 代码化视频组件、AI 技能、按词时间的字幕工具 | 复杂图形、字幕及可重复制作表达 | 不是视频理解模型，也不自动提供作品权限与恢复 |

依据为项目代码和官方资料，不是本轮实际复现评分。[O01～O09] 本文不将所有项目笼统称为“已实现稳定全自动导演”。

### 5.2 Hypit：价值在“观察—理解—表达”，不是一个神奇分析 API

Hypit 的参考规范要求把整片意图与局部细节相互校正，保留字幕、图形和声音系统的持续、变化和交接，并允许根据问题改变观察区间、采样密度和画面尺寸。镜头边界帮助定位，但跨镜头持续的标题、图形、配乐不能被每个镜头重复拆成独立系统。[O01]

其时间表达区分叙事事件和影片绝对时间：先定义有意义的片段或时刻，再依据实际对齐证据映射为组件可以消费的时间值。文字或表演变化时，共享关系可以重新解析，不必手工修改每一个消费者。[O02]

这与 Easel 的需求高度相关。但已阅读资料不能证明存在一个可靠的“输入参考视频 → 输出完整 DirectorAnalysis”的确定性端点；参考理解仍依赖 Agent、模型、工具和实际创作判断。引入 Hypit 的分析 CLI 与引入其完整创作工作流，是两种不同集成，不能混作一个收益结论。

### 5.3 OpenMontage：学习技能和反馈，不复制第二套权威

OpenMontage 的架构文件明确把 coding assistant 当编排者，Python 主要提供工具和持久化；Agent 读取阶段技能、调用工具、保存成果并审查。对 Easel 的启发是将专业创作方法变成可按需加载的技能，让模型知道如何调查问题，而不只是要求最终字段齐全。[O04]

但 Easel 已有普通用户 Web 产品、明确授权和可恢复任务。应该借鉴它的“创作过程”，而不是让外部 Agent 自行修改作品状态和授权表。公开架构文件、具体代码和最新演示可能存在时间差，本轮不依据 README 的样片成本或“全自动”表述推定性能与可靠性。

### 5.4 Agentic Video Editor：量化是补充，不是导演的全部

该项目 `style_copy.py` 确实从参考镜头长度统计、景别和运动重复比例推导部分风格参数。代码也明确说明，其 `bpm` 是镜头间隔推导出的节奏代理，不是真实音乐节拍检测；部分景别特征来自简化启发式。[O05]

Easel 可把镜头时长分布、重复率、构图偏好等作为解释和排序的辅助证据，但不应强制每个主题保持同一个镜头中位数，更不能把音乐节拍代理当作精确 BPM。真实约束如权利、已确认事实和素材可用性，不应仅作为一个可以被其他审美分数抵消的软惩罚。

### 5.5 当前 AI 能力改变了方法，但没有取消边界

官方视频理解资料已经提供原生视频输入、采样配置及部分自适应观察路径；Agent 技能可以承载专业程序知识；代码化视频工具允许 AI 创作具体场景组件。由此可研究从“一次性描述结果”转向“有工具的观察与制作”。不过，视频模型的内部采样、词语对齐误差、复杂转场理解和长视频一致性依然需要针对实际服务测试。[A01][A02][O09]

选择原则应是：把语义理解和创作选择交给适合的模型，把精确时间、文件身份、媒体检查和副作用控制交给程序；模型不确定时允许补充证据，而不是伪造高置信结论。更强的模型值得比较，但不能被用来替代缺失的授权、运行协议或真实质量证据。

## 6. 建议的职责与执行结构

### 6.1 一个业务控制面，多个受控能力，不是多个互相接管的系统

建议结构为：**Easel 业务控制 → 任务化创作委托 → 受控创作执行 → 原生制作工程 → 成片审阅**。这些是责任层，不要求新增五个服务、五张表或五个常驻 Agent。

| 责任 | 谁拥有 | 可以做什么 | 不能做什么 |
|---|---|---|---|
| 事实、确认、授权、版本、接受 | Easel 业务服务 | 绑定委托、记录用户决定、准入外部动作 | 让模型一句话改变权利或接受状态 |
| 参考理解、叙事、选材、编排 | 产品内创作 Agent | 按任务技能调用观察与制作工具，提出或落实方案 | 读取研发规则当人设，任意访问其他画像或凭证 |
| 候选供给、资格、复用与生成 | 现有 Material / Operation 能力 | 返回真实素材与缺口，按授权获取或生成 | 私自改故事，把候选等同于导演已选用 |
| 原生工程编译和渲染 | 选定 Editor 后端 | 检查、预览、渲染、报告错误和实际依赖 | 自行补付费素材，成为第二个作品 Owner |
| 技术检查、语义评价与最终选择 | 程序 + 审片模型 + Creator | 分别记录可测事实、审美判断、用户接受 | 用模型总分掩盖硬要求失败或代用户接受 |

这是对现有逻辑边界的深化建议，不是另建 V1 式中间协议链。[R02]

### 6.2 先增强受控执行，再决定是否换 Harness

第一候选是复用 `ModelTaskRunner`，按任务提供小而明确的工具：查看给定资产的某个片段、读取对齐文本、比较候选、检查草案工程、渲染局部预览、读取具名错误。工具只接受已登记句柄、允许区间和当前任务范围，不接受任意磁盘路径、凭证或任意网络请求。[C02]

技能内容应是创作方法与检查策略，按需加载，不把全部研发 AGENTS、历史诊断和架构文档作为每次模型输入。为每部作品保存足以恢复的创作摘要、未决问题和已验证成果，不能依靠长期聊天“记得”。这借鉴技能式 Agent 的方法，同时保留现有上下文隔离。[A02][V1-02]

如果现有 runner 无法提供合理的局部工程编辑、工具结果处理或有界恢复，再比较专门 Agent SDK / 通用 Harness。选择依据应是实际工具能力、文件和网络隔离、检查点恢复、真实调用效果及成本，不是某个框架名字。引入 LangGraph 之类的持久化机制也不自动解决外部调用的重复发送或业务授权问题；这些仍由 OperationService 等程序边界负责。[R02][A03]

### 6.3 原生工程不能被“共同最小字段”限制

当前 `EditProject.editor` 固定为 `ffmpeg-timeline-v1`。若以后采用 Hypit 或 Remotion，不能先把它们的语义组件、图形生命周期和动态排版全部压缩进现有 cut/dissolve/静态字幕结构，再声称支持了高级引擎。[C04]

建议只统一外围的业务绑定和产物说明：作品/方案修订、引擎标识与版本、原生工程引用、实际媒体清单、编译结果及输出身份。工程内部由该引擎的公共语言表达，错误由适配器转成有限诊断。是否需要修改公共接口，要正式做影响分析；本报告不宣称该抽象已实现。

每部作品固定一个明确的主要制作路径。可以组合本地媒体预处理和选定渲染器，但不允许两个独立总调度器分别发起生成、管理预算和确认成片，也不在某个效果不支持时静默改用低保真后端。

## 7. Director 应如何表达，才能既可执行又不僵化

### 7.1 三类信息，一份版本化导演资产

建议同一个 Director Revision 承载三类互补信息：面向用户的创作说明；带时间定位的参考证据与代表试片；少量需要被具体消费者执行的约束和适配边界。它们不必成为独立服务或三套可分别确认的方案。

| 信息类别 | 典型内容 | 消费方式 |
|---|---|---|
| 创作说明 | 叙事倾向、情绪变化、镜头与声音如何服务意义 | AI 理解并适配不同题材 |
| 证据与范例 | 参考片段、实际观察、推测、代表试片、适用限制 | 必要时复看、比较与解释，不每次重载全部原片 |
| 必要执行约束 | 用户固定项、已确认风格核心、关键事件关系、能力需求 | 程序绑定身份与范围，AI 实例化当前作品，编辑器落实 |

“可执行”的最低要求不是所有句子都有 JSON 字段，而是：关键意图有拥有者、有消费位置、有实现方式或明确缺口，并能在实际成片中检查。

### 7.2 必须区分四种约束强度

用户事实、素材权益和操作权限是不可以由创作权衡抵消的边界。用户已明确确认的硬要求以及导演核心承诺，发生实质冲突时应提出取舍。创作偏好和通常有效的手法可以按题材调整；具体实现选择则属于授权内的创作自由。这一分类直接回应 V1 的 C03，而不是为了提高通过率放松真实要求。[V1-01][R01]

例如“傍晚的沉静感”可能通过素材、调色、节奏、声音共同实现；只有用户明确要求某个真实拍摄时刻，或情节真实性依赖该时刻时，才可能成为源素材硬条件。不能把所有审美目标都转换为图库检索的必须属性。

### 7.3 用语义关系复用风格，不复制参考秒数

以下为假设性说明，不是实际视频分析结果：导演偏好“关键结论揭示时，让画面变化与字幕强调共同集中注意；音效只在确有帮助时使用”。科技主题可以在关键概念出现时切换示意图，职场主题可以在行动建议出现时切换人物或场景。两部作品不需要在同一秒切镜头，也不需要使用相同镜头数量。

| 同一规则的生命周期 | 当前作品应产生的内容 |
|---|---|
| Director | 适用情境、希望表达的效果、核心与可选部分、参考证据 |
| Planning | 本次具体哪一个观点或情绪转折适用；哪些内容与事实不能变 |
| Material | 该表达需要的真实视觉或声音候选；不可用时返回具体缺口 |
| Edit | 实际旁白或动作时间、所选素材、字幕和画面事件的时间映射 |
| Review | 事件是否发生、关系是否合适、是否服务新内容；哪些地方偏离 |

尽量复用现有场景、句段和 cue 身份。只有当前结构确实无法表达、且已有消费者需要时才新增语义事件对象。不要重新按 Markdown 行号建立场景，也不要让模型回抄全部来源与版本信息。

### 7.4 风格指标用于诊断，不自动成为新门禁

镜头时长分布、字幕停留、景别变化、声音强弱与画面事件关系可以帮助比较，但单个统计量不能代表风格。建议对 Creator 明确认可的关键特征记录“应体现、可调整、未适用及原因”，只对真实硬要求阻断。不要给每个自由度再设置一个模型评审，也不要为了固定分数牺牲内容表达。

## 8. Hypit、FFmpeg、Remotion：分层选型结论

### 8.1 Hypit 可以有四种不同的采用方式

| 采用层级 | 判断 | 进入条件 |
|---|---|---|
| 方法参考：分析技能、语义时间、组件思路 | 值得吸收，先独立研究 | 不把第三方技能中的权限、品牌和默认流程直接注入产品 |
| 分析工具：局部取帧、时间证据、转录等 | 与现有工具平等比较 | 同模型、同素材、同观察预算证明额外收益或维护优势 |
| 原生编排与渲染后端 | 认真保留，不能仅凭当前 FFmpeg 可运行就排除 | 目标风格需要，公共接口、隔离、局部修改与验收可行 |
| 整体替代 Easel 的业务编排和状态权威 | 当前不建议 | 与已确认 Web 产品、授权和恢复需求不匹配；不能重复造 Owner |

Hypit 旧适配的耦合风险和新公开能力是两个问题。应重新验证选定版本，而不是直接迁回 V1 绑定内部源码的实现；也不能从旧接入证据不足推导 Hypit 本身做不到纯制作。[V1-04][O01～O03]

### 8.2 各引擎的合理位置

| 方案 | 值得采用的情况 | 主要代价 / 风险 |
|---|---|---|
| 当前 FFmpeg 受限时间线 | 剪辑、裁切、已有转场、基础字幕与独立音轨足以表达目标 | 当前适配表达范围有限；扩展过多可能逐渐自建编辑语言 |
| 扩展 FFmpeg 工具能力 | 小范围效果缺口可用公共滤镜和清晰参数补齐 | 必须维护检查、预览和局部修改，不能变成任意 filter 字符串注入 |
| Hypit 原生制作 | 语义时间、组件行为或复杂参考表达确实有优势 | 原生语言学习、版本接口、运行隔离、许可与接入成本 |
| Remotion 原生制作 | 动态排版、信息图形、组件动画和代码化视觉占主导 | Node/浏览器渲染、工程依赖、原生代码沙箱与许可证条件 |

这是一张能力匹配表，不是实测性能排名。FFmpeg 是底层媒体工具，Hypit 是更完整的创作与制作体系，Remotion 是代码化视频制作技术；把三者简单当作相同替代品会误导选型。[C04][O01][O02][O09]

### 8.3 许可、平台和当前账户分别处理

读取的 Hypit 许可证是附加条件的 Apache 2.0 文本：本组织自身用途与部分单租户使用有许可空间，多租户、向第三方提供相关托管能力及商业再分发等另有条件。不能把它当作无条件宽松 Apache 依赖，也不能据此认定个人本机创作不可使用。Remotion 的具体许可同样依组织和部署形态核对。最终引入以精确版本的许可证和实际使用方式为准，本文不作法律结论。[O03][O09]

本机 CPU、内存、GPU、中文字体、浏览器与模型服务是否就绪，必须独立验证。WhisperX 文档里的高吞吐或 GPU 配置，不是当前 Mac 的性能承诺。模型、素材、配音订阅的权益不等于另一个新 Provider 的授权；但已明确允许复用的账户和配置也不应在每次研究里反复索取。[O08][R01]

## 9. 如何验证选型，避免再做一轮长调试

以下是支线试验设计，不是新主线任务，也没有在本轮执行。开始前需要明确参考素材、允许使用的服务、试验范围和生成次数；不以研究名义隐式调用付费服务。

### 9.1 先分离“观察更好”与“Agent 更强”的作用

| 对照 | 保持不变 | 唯一重点变化 |
|---|---|---|
| A0 当前基线 | 相同参考、任务、模型、输出目的 | 现有固定观察与一次性分析 |
| A1 自适应观察 | 尽量保持模型、目标和输入上限可比 | 给模型受控复看片段与补充证据能力 |
| A2 专项证据 | 相同参考、模型和评价样本 | 增加镜头候选、实际语音时间与统一时钟 |
| A3 Hypit 分析工具 | 相同模型、参考及证据预算 | 使用 Hypit 的具名分析能力 |

如果 Hypit 原生工作流必须采用不同模型、更多人工步骤或另一套创作程序，应单列为“完整方案对照”，不能把差异全归因于 Hypit 工具。原生视频模型与工具取帧也应明确采样和输入量，不能一边看完整密集证据，一边只看少数截图后宣称算法胜出。

评价应看关键变化是否被正确定位、观察和推断是否区分、跨题材规则是否有用，以及耗时、调用、输入规模和人工标注成本。镜头检测误报与漏报要同时计入；不以分析篇幅、专业词数量或模型自评分决定胜负。

### 9.2 用少数关键效果比较制作后端

先从用户参考中挑选真正决定风格的效果，例如语义揭示与字幕强调同步、跨镜头持续的图形系统、局部修改后声音与其余内容保持。固定相同资产、文字、声音与目标，在当前 FFmpeg、Hypit 或 Remotion 的隔离试验中比较可表达性、局部迭代次数和最终表现。

这一试验可以只制作能够展示关键行为的局部片段，不需要重新构建全部 Easel；局部成功也不能替代 1～900 秒等正式范围。若当前后端确实无法表达核心风格，应明确进入后端选择，而不是强迫用户接受简化版本。若现有后端足够，则没有必要为了先进架构而引入第二个编辑器。

### 9.3 产品目标必须通过跨题材、重复运行来检验

建议把“2 种导演风格 × 3 个内容主题 × 2 次运行”作为后续可讨论的 12 个样本试验设计，其中包含未用于调优的主题。它只是便于分析的初始样本量，不是正式批准次数，也不具备自动证明长期稳定的统计效力。

每个样本应独立记录：是否从正常 Web 输入完成；是否有研发救场；Creator 是否接受该具体版本；风格是否可辨识且内容没有套模板；硬要求、权限和素材使用是否合规；哪些失败属于正确拒绝、哪些属于误阻断或工程错误。失败样本不能事后换题删除。

| 指标 | 计算或记录口径 |
|---|---|
| 自主完成率 | 无研发介入得到真实可审阅首版的样本 / 事先固定的可执行样本 |
| 自主接受率 | 无研发介入且被 Creator 接受的样本 / 同一固定样本集 |
| 风格与内容质量 | 关键风格表现、叙事适配、事实忠实分别评价，不只比较像不像参考 |
| 误阻断 / 合法拒绝 | 分开统计并保留原因；正确拒绝不记成片成功，也不当工程缺陷 |
| 局部修订保持率 | 指定变更完成，同时未要求变化的声音、文案、版本和素材得到保护 |
| 效率 | 每个可接受自主作品的模型调用、媒体提交、耗时和人工分钟；失败成本不隐藏 |

时间容差、风格量表、接受标准和样本范围应在试验前明确。定量特征可辅助独立或盲序审阅，但不把一个模型评委的高分直接当作 Creator 接受。[R01][V1-02]

### 9.4 何时继续、何时停止

当新工具明显补齐重要证据、减少真实错误或节省可比较成本，才考虑迁入产品；当收益只体现在描述更长、测试更多或单条演示更好看，而授权、恢复和用户交互明显变差，应停止扩大集成。若所有方案都失败，应记录失败层次，允许将问题定位到素材、模型能力或需求与制作能力不匹配，而非不断更换总体框架。

## 10. 主线之外的最小演进建议

研究不应因为“现在只做支线”而失去可落地性，也不应悄悄生成主线任务。下面给出候选依赖关系，供后续单独决策。

| 候选改动 | 优先理由 | 本轮不做的事项 |
|---|---|---|
| 创作模型与媒体协议能力核验 | 缺真实多模态能力时，其余导演分析结论没有运行基础 | 不静默换模型，不提交真实请求 |
| Director / Edit 的受控观察与局部试编排 | 复用现有 runner，直指一次性返回的局限 | 不新建通用 Agent 平台，不开放任意 shell |
| 语义 cue 到实际音画时间的绑定 | 解决“时间合法但意义不同步”的候选风险 | 不重写已确认方案，不提前冻结公共 Schema |
| Director 证据、风格说明与少量执行关系 | 增加关键意图可追踪性，同时避免规则爆炸 | 不为全部形容词创建硬 Gate |
| 原生制作后端比较 | 由真正需要的风格能力决定是否引入 Hypit / Remotion | 不迁旧 Hypit parser，不同时实现三套完整后端 |
| 跨题材和失败恢复样本 | 评价最终用户价值，避免再次停留在软件 PASS | 不把研究样片记作主线验收 |

公共合同不是永远不能改，但不能因为内部实现方便而反向改写需求。每个拟迁入改动都应列出：原要求、已证实缺口、受影响消费者、已有版本如何保留、哪些测试能证明没有新增误阻断。确实需要结构性调整时可以调整，不必把所有变化伪装成内部小补丁。

## 11. 对前面讨论的修正与最终立场

此前“先跑起来”和“先做 Director 研究”被表达成了近似二选一；现在更准确的判断是：**真实闭环验证系统运行边界，支线试验验证创作表达上限，两者解决不同的不确定性。** 主线按用户当前授权推进；支线不设新的主线门禁，但可以提前识别明显不满足关键风格的能力缺口。

此前把方向概括为“FFmpeg + 更多结构化 Director 规则”，还不够完整。结合 V1 教训，应改为：**最小必要结构化 + 可理解的创作说明 + 实际参考证据 + 受控工具迭代 + 语义时间落地 + 真实成片评价。** 结构化不是越多越好；自然语言也不是可以没有消费者和执行反馈。

此前“不建议整体采用 Hypit”仍适用于业务权威层，但不能扩大为“不需要 Hypit 原生制作能力”。V1 的历史失败不足以否定 Hypit；V2 当前后端可运行也不足以证明它能实现全部目标风格。应把 Hypit 放回恰当的责任层，与替代方案通过相同条件竞争。

**最终建议：保留 V2 的业务内核，不回滚 V1；优先验证受控创作执行和语义时间落地；Director 保持创作自由与必要约束并存；当前 FFmpeg 是运行基线，Hypit 与 Remotion 是按需求竞争的原生制作候选。**

本文完成的是设计选型的独立静态研究及试验方案。真实对照、最终后端选择、模型路由配置和正式公共合同仍未冻结。研究建议不构成修改主线或执行真实调用的授权。

## 12. 外部工程案例补充：得物技术“动态规则 Agent”（2026-10-17）

> **研究性质：外部工程方法类比，不是新的 V2 需求、ADR、实施合同或真实验收结论。** 来源是得物技术 2026-10-15《动态规则的 Agent 实践：用确定性工程驾驭 LLM 的资产智能验收》（[O10]）。原场景是财务资产/合同附件核验，并非视频创作；下面的 Easel 映射均为本支线的候选研究判断，未在 V2 真实作品中验证。

### 12.1 文章值得借鉴的工程机制

该案例将持续变化的自然语言验收规则配置化，LLM 负责非结构化材料事实提取和按规则比对，确定性程序管理编排、幂等、数值核对、异常兜底与可追溯结果。系统区分正式、试跑、回测流量，通过人工反馈与回测验证规则调整，并对少数关键误判引入多模型复核。[O10]

**Easel 最应吸收的是：动态规则具备版本、来源、隔离试验与回归证据；而不是把固定财务判定流程或多模型投票直接移植进视频创作。** 财务审核追求可判断的事实一致性；Director 还承担开放的叙事、审美、选镜和音画表达。

| 外部实践 | 对 Easel 的可能价值 | 不照搬的部分 |
|---|---|---|
| 文本规则配置与版本管理 | Director Revision 保留表达原则、参考依据、适用边界及接受记录 | 不要求每条审美偏好都拥有新的强制字段 |
| 事实提取与规则判断分开 | 参考媒体的镜头/语音时间证据和模型风格解释分开；成片观察与推断分开 | 不复活 V1 A/B/Truth 多批大规模重复审核 |
| 正式、试跑、回测隔离 | 候选导演分析、小试片与正式作品使用不同用途、版本和回执 | 不复用未授权生成次数，不把试验结果冒充正式质量 |
| 反馈和标准答案 | 保存版本绑定的具体 Creator 风格意见、作品反馈与已观察媒体证据 | “接受/不接受一条作品”不等于全部风格规则的二值真值 |
| 结构化判断及来源可追溯 | 对关键导演特征追踪参考区间、计划落实、真实编辑及成片证据 | 不让模型反复回抄程序已知的所有 ID / Schema |
| 多模型投票 | 仅在少数可客观核验的高风险判断中作为候选 | 不对所有审美意见多模型投票，防止增加调用与误阻断 |
| 异步、幂等与兜底 | 佐证现有 Work / Task / Operation / UNKNOWN 设计方向 | 不因此另建控制面、第二业务 Owner 或状态机 |

### 12.2 对照 V1 的失败归因，必须吸收与必须避免的经验

- **C01 冻结保存不等于下游真正消费。** Director 风格版本被持久化且 hash 正确，不证明 Planning、Material、Editor 都收到了适用范围和真实风格意图。应检查每一重要特征的实际消费者与依据，不通过复制整份长上下文“补齐”。
- **C02 / C05 文本位置当镜头身份、重复上下文与模型回抄。** 程序绑定作品、场景、输入与资产身份；模型主要产生创作判断和局部理由。规则版本回归不能重新变成几十个机械问题或多个重复长批次。
- **C03 Creator 硬要求与导演偏好混淆。** 对视频来说，“傍晚的沉静感”“变化节奏快”可能是后期或镜头组合可实现的意图，不代表原始图库素材必须自然具备这些属性。明确区分 Creator Hard、导演核心要求、可适配偏好、后期能力与素材 Rights；正确的 Hard 和权益阻断继续保留。
- **C06 / C07 恢复、来源和授权边界。** 可以复用仍合格的观察与资产，但不得继承不同作品的授权，不能把已搜索候选等同实际选用或合法可用素材。UNKNOWN 仍核实原操作而非盲重发。
- **C08 / U7 软件 PASS 与真实自主生产不同。** 导演规则调整后的回归必须分别记录 SOFTWARE、REAL_PRODUCTION、AUTONOMOUS 和 CREATOR_ACCEPTED，记录真实失败和人工介入；不拼接跨版本片段，拒绝所有正确阻断不等于提升产品质量。[V1-01][V1-02]

### 12.3 对 V2 的最小增量建议，而非新增平行系统

V2 已有 Director Revision、用户风格确认、试片/版本接受、冻结 PlanDocument、FrozenIntentCompiler、CreativeEdit、FFmpeg EditProject 和分段 SemanticReview。文章带来的研究增量，应着重回答：

1. **Director 具体保存什么？** 继续保留创意说明、参考区间、代表试片与适用边界；少数决定性风格特征可研究“语义触发 → 建议表现 → 约束强度 → 来源证据 → 制作能力”这种受控投影，**不是立即冻结大型导演 DSL 或增加公共 Plan 必填字段**。
2. **制作链是否消费规则？** 针对具名关键特征，检查 Planning 是否安排了适合本主题的镜头设计、Material 是否按真实 Need 选择素材、Editor 时间线是否体现变化、成片是否有实际可观察证据。允许合理适配，也必须报告真实能力缺口；不建立多层模型统一给全片评分的重复系统。
3. **反馈如何正确绑定？** 将作品具体内容问题与 Director 风格问题区分。对用户明确允许保留的试片和反馈，按实际 Director/作品/媒体版本保存研究样本。用户拒绝一条视频，不证明整个导演版本错误；接受一条视频，也不证明跨题材稳定。
4. **版本迭代如何安全试跑？** 未接受的候选版本与已接受版本并列比较；能复用的事实证据先复用；需要新增生图、生视频、TTS 或外部服务时，仍走 Easel 原有授权和次数控制。新版本不得静默覆盖频道默认、历史作品、已确认方案。
5. **什么交给确定性程序？** 身份、权限、素材引用、时间线和音轨基本约束由程序守护；叙事、表现手法与最终选材由创作 Agent 做判断，并允许受限工具观察、试编排和局部修正。

### 12.4 预研原则与建议验收方法（未批准实施）

| 编号 | 支线原则 | 未来试验需要验证 |
|---|---|---|
| P1 导演版本与证据绑定 | 同一 Director Revision 的参考依据、关键规则、代表试片与具体用户反馈能被核对 |
| P2 AI 创作自由 + 程序硬边界 | 不将风格偏好无端升级成素材 Hard；真正事实、Rights、授权仍不被放宽；失败理由可定位 |
| P3 小范围隔离试片与回归 | 同版不同主题比较风格与内容适配，同时单独记录自主完成、Creator 接受和实际成本 |

试验应观察导演拆解误判、风格规则能否落实到作品、人工修订次数、误阻断与正确拒绝、模型调用和单部可接受作品的总成本。没有真实样片前，不先设自创的风格一致率门槛，不自动创建长期作品记忆或跨作品学习子系统。

**对选型的影响：得物案例提供“动态规则的生命周期与质量工程”方法，而不是镜头检测、语义编排或渲染后端。Hypit、FFmpeg、Remotion 仍按本文 §7–§9 的能力分层和真实对照选型；本次案例不改变“保留 V2 业务控制、避免整体迁回 V1”的结论。**
