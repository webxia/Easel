## 权威与冲突处理（不是简单文件优先级）

- **产品目标和可观察行为**：已确认的需求与用户最新明确决定。想改变产品要求，先确认变更及影响范围。
- **系统责任和长期设计**：已接受的架构/ADR。源码不自动改写已接受决策；合理的重构通过正式修订替代旧决定。
- **本次可执行操作**：用户授权与活动 Task。Task 不能扩大授权或绕过安全、凭证和预算边界。
- **当前代码实际行为**：具体 Git 版本的源码、测试和运行证据。失败和实现缺口必须原样记录。
- **当前进展**：`04_CURRENT_STATE.md` 的索引和结论；只有指向具名证据时才有事实依据，不能覆盖原始证据。

当两者不一致：先记录冲突的要求、源码/证据和影响；属于实现缺口则修实现，属于需求改变则修改需求并复审相关架构；不能靠“文件较新”或“测试过了”静默胜出。

## 保持内容短且可演进

1. 同一事实只有一个维护位置，其他文档链接引用；历史任务信息留在 Git/Task/PR，不在文件顶部层层追加“最新”。
2. 新的正式需求要有稳定 ID、行为和验收；Task 只处理其中一部分且有明确完成边界。
3. 没有实际决策或执行任务，不创建空 ADR/Task；小改动可只记录 PR。
4. 不将方案里的候选细节、假设指标和旧二开协议误写成已实现/已获批准的事实。
5. 模型输出、文档检查、实际视频产物、Creator 审片是不同级别的证据。
