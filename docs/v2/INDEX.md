## 权威与冲突处理（不是简单文件优先级）

- **历史目标、历史实现与运行结果**：V1 固定版本源码、用户决定、历史 ADR、Task 和具名回执；在 S2 归因，不自动迁为 V2 需求。
- **本次产品目标和可观察行为**：用户在 S4 明确确认的正式需求与最新明确决定。原 `01_REQUIREMENTS.md` 中的候选不是自动批准的本次需求。
- **系统责任和长期设计**：仅经 S5 正式评审批准的架构/ADR；当前方向稿与旧设计只可作参考。
- **本次可执行操作**：用户授权与活动 Task。Task 不能扩大授权或绕过安全、凭证和预算边界。
- **当前代码实际行为**：固定 Git 版本的源码、测试和运行证据；不能让文档愿景或历史作品覆盖当前事实。
- **当前进展**：`04_CURRENT_STATE.md` 的索引和结论；只有指向具名证据时才有事实依据，不能覆盖原始证据。

当历史与当前冲突：先分别保留历史事实、当前事实和本次需求；S2 负责归因、S3 负责经验提炼、S4 决定需求生效范围、S5 再作设计取舍。不得因“文件更晚”“测试较多”或“旧系统已经实现”跳过确认。

## 保持内容短且可演进

1. 同一事实只有一个维护位置，其他文档链接引用；历史任务信息留在 Git/Task/PR，不在文件顶部层层追加“最新”。
2. 新正式需求要有稳定 ID、行为和验收；历史需求保留独立来源，不将旧 V1 实现协议当新需求。
3. 没有实际决策或执行任务，不创建空 ADR/Task；小改动可只记录 PR。
4. 不将候选架构、假设指标、V1 旧生产合同或故障机制误写成已实现/已获批准的 V2 事实。
5. 模型输出、文档检查、实际视频产物、Creator 审片是不同级别的证据。
