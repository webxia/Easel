## 0. 本文职责、边界与有效范围

本文是 S2–S5 的**唯一研究顺序、证据规则、准入与交付约定**，不再建立另一套并行阶段流程。总体里程碑见 [路线图](03_ROADMAP.md)；真实推进情况只看 [当前状态](04_CURRENT_STATE.md)，不能把本计划存在等同于 S2 已验收。后续如需补充阶段研究结论，可在本文对应区补齐或以明确引用关联一份结果报告，避免为每个失败新开重复 Task。

- **S1 提供当前代码事实**：源码能力、工程质量与适用边界。S1-A 尚在 [PR #1](https://github.com/webxia/Easel/pull/1) 评审；S1-B 尚在 [PR #2](https://github.com/webxia/Easel/pull/2) 评审。它们的事实只对各自固定 SHA 与测试环境成立，**不等于需求批准或设计选择**。
- **S2 提供 V1 历史认知**：完整还原当时的目标、已确认与未确认需求、设计理由、实现、成功、失败、演进、修复效果和原因；本阶段**不作 V2 最终复用/删除/技术选型决议**。
- **S3 提供可迁移的经验与历史需求认识**：区分业务需求、规则、工程经验、实施细节和待证假设；形成候选认识供用户判断，**不自动继承为本次需求**。
- **S4 才确认本次需求与事实输入**：用户录入或明确认可本次产品范围、验收和约束；汇编经确认的需求与 S1/S2 的事实，并记录冲突、未知、限制。未经确认的旧 `1～900 秒`、四声音模式及候选技术方案仍是历史或讨论资料。
- **S5 才决定怎么设计**：在 S4 完成后对照备选方案，再明确哪些原则保留、当前底座哪些实现复用、哪些重做/舍弃，评审并冻结架构。`ModelGateway`、`Context Manager`、`Production Kernel`、`ConfirmedCreativeSpec` 等名称均可作为候选，不因 V1 曾建议就自动成为必建模块。
- **S6/S7 才实施和验收**：按已批准设计实施真实 Web 创作纵向闭环，然后依据真实结果优化和做确认范围内的完整验收。

**全阶段禁止**：修复或续跑旧 V1、自动迁移旧协议/旧 Attempt/运行状态、把历史失败当新开发任务、以局部软件 PASS 冒充真实自主出片；未经另行授权不进行真实付费模型/媒体、发布、远端不可逆动作、生产数据迁移或上游合并。

## 1. 四个“对象”不能混淆

| 对象 | 应当回答 | 来源与权限 | 不代表 |
|---|---|---|---|
| **历史目标/历史需求** | V1 当时到底想做什么、为何而做、曾如何变化 | V1 用户记录、需求、ADR、Task、产品目标与验收；标注确认层级 | 本次 V2 已批准需求 |
| **历史事实/因果归因** | 当时什么版本实际执行、发生了什么、为什么 | 固定 Git SHA、源码、原始请求回执、验收与时间序列 | V2 必须采用某个修复方案 |
| **经验/候选认识** | 某机制在什么条件下有效；有什么教训和未知 | S2 对正反样本的归因与反证；S3 抽象 | 直接变成工程规范或架构决议 |
| **本次需求/设计决定** | 当前用户要什么、接受什么约束、怎么实施 | S4 用户明确确认；S5 方案比较/ADR 与验收 | 由旧代码、旧测试或旧文档自动决定 |

不得从“某阶段丢失授权信息”直接推断“必须建立新 Context Manager”；不得从“Material Ready 阻断”直接推断“Rights 检查应放宽”；也不得从“旧工程已做过”直接推断“V2 应保留旧执行接口”。

### 2.2 证据等级与认定顺序

对每个重要判断注明证据类型与适用范围：

1. **确认的历史事实**：有固定版本源码、原始输入/输出或媒体字节、实际运行回执和直接支撑的范围。事实可为成功，也可为失败；**事实成立不等于原因已经确定**。
2. **有支持的因果归因**：可指出明确机制，且有源码因果路径、前后对照或真实失败→针对修复→相关行为改善的证据，同时说明不能推出的结论。
3. **待验证假设**：缺少对照、仅在单一题材/环境观察，或仍有模型、提示词、Provider、Runtime 等竞争性解释；必须保留反证可能。
4. **不成立/已推翻结论**：已有相反证据；记录旧判断来源以及被何种新证据否定，不删除历史说法。

实际结果分开：`DESIGNED`、`IMPLEMENTED`、`OFFLINE/SOFTWARE_PASS`、`RUNTIME_LOADED`、`REAL_PRODUCTION_PASS`、`CREATOR_ACCEPTED`。保留 `FAIL/BLOCKED/UNKNOWN/NOT_TESTED`，不能将跨版本局部 PASS 拼成完整 E2E；HTTP 200/SSE 结束不等于合法 Tool Arguments，更不等于领域准入。

### 2.3 历史需求的来源等级

历史需求应按**当时**版本记录：用户明确决定 / 已接受需求或 ADR / 讨论候选 / 工程师或 Agent 推导 / 测试临时假设 / 已修改或撤销。较新的设计文档不能无证据追认更早的决策；实现存在也不能证明当时用户批准该行为。旧用户授权、预算或发布权从不随需求复制至 V2。

## 3. S2-A｜完整项目历史与需求演进还原

**要解决**：不仅找到失败，更重建 V1 从项目意图到最后封存的完整路线与每次重要转向。

工作内容：

- 从最初业务目标、明确的用户决定、已接受 ADR、架构版本、Task 与验收，构建**历史需求演进链**；区分原始目标、阶段范围、后来修订、未确认想法和纯实现细节。
- 建立关键时间线：Creator/Director、Creation/Hypit、Material、Preparation/Planning、New-Only、真实 E2E、合同治理与暂停；每个节点记录为什么改变、改了什么、实际效果。
- 为核心概念（Creation/Attempt、Proposal、MaterialNeed、Rights、Review、Build、质量、预算、会话等）建立“历史语义、来源、当时实现和变更历史”的索引。
- 已有的 22 项缺陷作为**负例候选**映射至上述时间线；主动搜寻正例与被解决的问题，而非只复述最后的失败状态。

交付给本文件的 **S2-A 研究结论**：需求来源及变更索引、重要架构决策及替代路线时间线、已证实版本清单、重大节点证据入口、无法确定的历史事实。**不得写入“V2 必须创建哪个模块”。**

### S2-A 完成条件

每项重大历史目标/决策能指出首次提出、确认层级、至少一个实际版本、对应测试或运行边界；影响视频主线的转折不能只用最后一篇 Current State 概括。没有证据的地方明确标为未知，不为覆盖率猜测。

## 4. S2-B｜按真实视频作品还原端到端运行链路

以一个端到端作品的正常用户路径为主轴：

`Creator 输入/修改/确认 → Preparation/规划及 Truth → Material/候选/Rights/实际供应 → Authoring/Hypit Check/Build/Export → Quality/Review/反馈/保存`。

每个环节统一回答六个问题：

| 维度 | 具体问题 |
|---|---|
| 初衷与合同 | 用户或已接受设计当时要求什么？允许什么创作自由度？ |
| 实际入口与 Owner | 真正执行的代码、接口和状态权威是谁？ |
| 上下文与交接 | 输入哪些确认事实、版本与权限；实际给下游什么；遗漏了什么？ |
| 软件与原始证据 | 哪些仅为 fixture / 单测，哪些为真实模型、Provider、媒体或人工审片？ |
| 成功/失败位置 | 到了哪里、保留哪些局部成果、发生怎样的停止或合法阻断？ |
| 版本与成本 | 是否同一受测源码/配置/协议；时间、调用、人工参与和原费用记录边界如何？ |

**至少对照三类典型样本**：

- 曾完成 Creator 审片与实际入库、但开发过程中有人修代码或重载服务的作品：单独评价功能、用户自主性、恢复性、UI 暴露与风格质量。
- New-Only 的本地 50 秒 MP4 软件集成：明确使用了哪些固定外部回执，哪些真实 Hypit/媒体/内部权限通过，哪些**没有**完成真实 Web 创作。
- 代表性完整 Planning 失败（如 R09–R19 的相同题材多 Attempt）与 Material/BGM 失败：比较真实阻断来源、已实现的修复、验证边界，不把多个重试冒充跨题材完成率。

同时搜寻稳定成功正例、明确的正确拒绝与有效冷恢复，不能仅挑选反例。

### S2-B 完成条件

主线每个环节具有至少一项**有界**代码/运行/验收事实或明确未验证声明；可回答“V1 哪些媒体能力确曾成功、主线在哪里停住、哪些问题从未真正执行到”。不要求重新运行已封存的模型、Build 或验收。

## 5. S2-C｜因果归因、修复收益与复杂度演进

**归因必须把“症状、直接原因、放大因素、最终未完成结果”分开。**不能从“Planning 未通过”直接否定 Material/Hypit 的全部设计；也不能将“Rights 阻断”自动称为误判。

现有 22 项问题可作为调查分组（非已定案的六个唯一根因）：

| 研究簇 | 历史问题编号 | 当前待验证问题 |
|---|---|---|
| 创作语义、委托与上下文投影 | 01、03、04、07、08、21 | 是冻结原文、投影、Prompt、模型责任，还是审核规则导致信息遗漏或无效约束？ |
| Scene/Need 表示和审核膨胀 | 02、05、09 | 是业务身份错误、机械展开、重复证据，还是必要的语义审查？ |
| 工具、终态、恢复、预算与状态 | 06、10、11、12、13 | 是模型生成、接口协议、运行时隐藏重派、预算预约还是 Owner 竞争？哪些复现过？ |
| 素材、语音、音乐和权益 | 16、17、18 | 缺真实资源、观察能力、证据转移还是状态展示？何种阻断是正确行为？ |
| E2E、Creator 自主与产品范围 | 14、15、19、20 | 什么确实完成，什么只完成软件集成；什么实际上并未验证？ |
| 历史兼容与演进成本 | 22 | 哪些双轨和多轮补丁是阶段性合理取舍，哪些后续缺少收益证明？ |

**每个重要归因用一条记录表达：**

| 字段 | 填写口径 |
|---|---|
| `HIST-ID` / 历史需求 | 标识稳定、对应当时的具体目标/约束，不使用新的 V2 需求 ID |
| 现象和受影响范围 | 哪一个作品、阶段、版本、批次、用户体验或安全边界 |
| 机制与可能原因 | 区分程序组装、模型输出、供应/运行时、业务合法阻断等层次 |
| 正面证据与反面证据 | 固定版本的源码行/原 Capture/验收；至少主动寻找一种竞争解释 |
| 曾实施的修订 | 什么代码或提示改变、真实加载与否、仅离线还是实际复验 |
| 实际收益与代价 | 解决了什么、未解决什么、额外请求/上下文/状态/人工负担 |
| 结论可信度与未知 | 事实成立、因果已支持或仅是假设；不可外推的范围 |
| 历史经验候选 | 从案例可能抽象的原则，**暂不填写 V2 必建组件或修复任务** |

三条防止错误归因的规则：

1. “重复上下文导致本地 Repair 容量错误”可有较充分证据；“去重已经提高真实 Planning 全链完成率”若没有对应真实结果就不能写成结论。
2. “通用 OpenClaw 人格混入专用 Planning”可被请求原文证明；是否**直接造成零工具**必须另有对照。
3. “正确阻断了 Rights UNKNOWN、Creator 授权或来源冲突”是安全结果；真正可能有问题的是错误分类、缺证据、无必要升级或无法合法补料，不能为了减少失败量删除保护。

### S2-C 完成条件

每项主要负例和正例均有**版本化证据、原始现象、原因可信度、竞争解释、修复后验证范围**；对尚未解决的归因可标记待验证，不必强行得到唯一原因。应解释为何复杂度形成、哪些实际减少负担，而不是用“旧系统太严格/模型不行”替代分析。

## 6. S2-D｜历史认知收口（不是 V2 继承决策）

S2 最后整合为四个**历史事实维度**：

1. **成功资产地图**：明确当时有效的产品能力、领域边界、代码机制、测试策略和受验证条件。
2. **失败/阻断因果地图**：已定位缺陷、合法拒绝、集成缺口、未证实设计风险分离；记录怎样相互放大。
3. **历史需求与设计演进谱系**：哪些为用户原始要求、后来批准的修订、讨论中断的目标或工程自加限制。
4. **开放问题及证据缺口**：未知的真实 Provider、正式端到端、预算对账、规模化、质量、归因等；不要伪造结论。

**S2 允许输出**：“某条原则在具名 V1 版本中被证明对某种失败有效”“这个旧实现制造了重复问题”“某路径未验收”。

**S2 不允许输出**：“V2 必须采用 ModelGateway/单一新内核”“立即修复 22 项”“直接照搬 Material V1.3 所有 Schema”“最终删掉某个现有官方模块”。

### S2 准入 S3 的退出检查

- 需求/ADR/架构演进与主链相互关联，有记录来源和版本；
- 22 项既有问题逐条**已归类、合并关联或标记待证**，不是简单全部接受；
- 成功作品、失败作品、正确阻断和真实 E2E 缺口均获得代表性证据；
- 已区分事实、归因、假设、修复效果，保留反例和未验证边界；
- 私有数据与 V1 原件仍独立保全，V2 Git 无原始运行内容；
- 用户审阅历史认知基线后，才进入 S3。

只要满足研究覆盖与可追踪性，**不要求**对 215,318 个证据文件全部逐字节读取或让历史模型再跑一次。

## 7. S3｜从历史事实提炼经验，完整还原需求认识

S3 不是“选择 V2 技术”，而是把 S2 的案例转换为**可供本次需求确认的认识**：

| 产物 | 提炼方法 | 当前权限 |
|---|---|---|
| 历史产品需求清单 | 从用户决定、旧已接受合同、变更历史还原需求与验收；注明“当时有效/后来修订/从未批准” | 仅历史认知，不成为本次 V2 需求 |
| 业务约束与创作自由度 | 从合法拒绝、Creator/Director/Truth/Rights 经验抽象义务、允许调整和人工决定边界 | 候选原则，保留适用条件 |
| 工程与 Agent 使用经验 | 从上下文、结果捕获、状态、测试、预算、恢复、权限案例归纳可验证惯例 | 阶段三规范候选，不立即修改 `AGENTS.md` 或 CI |
| 实现与流程经验 | 解释什么时候分层、何时减少调用、如何确认真实交付、什么机制制造冗余 | 不当作已选择的架构 |
| 待确认矛盾与问题 | 对历史需求与当前目标/可用代码不一致的部分列出选择项、影响和风险 | 交给 S4 用户确认，不擅自决定 |

重点区分：**业务目的/必须遵循的安全义务/历史实现手段/阶段性测试阈值/用户体验偏好**。历史示例“最长 900 秒”“四种声音模式”“固定多批 B Review”不能一律升格；前两项若属过去的业务目标，需在 S4 重新确认；后者更可能是历史实现策略而非产品需求。

### S3 退出检查

每项经验能够反向追溯到 S2 的具体案例及证据，并描述**适用条件、已知反例、收益与代价**；历史需求来源与确认层级清楚；工程规范建议独立于业务需求。不得把“经验被总结”写成“V2 必须采用该实现”。

## 8. S4｜本次 V2 需求正式确认与事实输入冻结

**S4 的起点**是用户重新录入或明确逐项认可这一次的需求，而不是旧 V1 的条目自动生效。现存 [需求文档](01_REQUIREMENTS.md) 与 [架构方向稿](02_ARCHITECTURE.md) 在此以前只能作为讨论候选。

**待合并文档的元数据冲突**：V2 主线早期的需求文件曾被标记为“CURRENT / 已确认的目标需求”，但最新用户决定是**本次 V2 需求尚未正式录入**；S1-A PR #1 已将这一状态更正为 DRAFT。PR 未合并期间不得依赖旧标题/旧优先级直接启动设计。已有架构方向稿也不是 S5 正式方案。未来合并这些 PR 时应语义收敛元数据和导航，而非机械覆盖。

应当由用户明确回答（可分批确认）：

- 产品目标、首个可用体验、Creator 中途交互和自主程度；此次优先做什么、不做什么；
- Creator/Director/Content 的业务责任，硬要求、允许导演适配的范围和必要审批；
- 视频形式、声音、时长、素材来源、Rights、授权、付费与自动发布的当前范围；
- 成功的可观察标准：真实 Web 首版、Creator 审阅与接受、合法拒绝、失败恢复、效率等；
- 上线阶段、非功能要求、可用预算/运行条件与不能改变的安全限制。

建立一个**本次正式输入基线**，其中必须同时包括：

| 输入类别 | 权威与状态 |
|---|---|
| `CURRENT_REQUIREMENTS` | 用户本次明确批准的需求 ID、优先级、验收、范围及不做事项；由需求文档维护 |
| `CURRENT_SOURCE_FACTS` | S1-A/B 对固定代码版本的源码能力、质量风险、实际运行/测试限制；若官方有更新，重新确认分析差异 |
| `HISTORICAL_LESSONS` | S2/S3 的历史事实、成败归因与经验，标注已证实/推断/待验证；不是新业务权限 |
| `OPERATING_CONSTRAINTS` | 本次可用模型、Runtime、素材源、环境、费用、Rights、人工授权、安全和性能范围 |
| `OPEN_QUESTIONS` | 历史结论与本次需求的冲突、无证据的技术能力、未能确定的性能/成本；记录负责人及决策时点 |
| `ACCEPTANCE_EVIDENCE_PLAN` | 需要怎样的真实成功/拒绝/恢复样本证明本次产品完成；软件/真实/Creator 接受必须分开 |

**需求与输入冻结的含义**：上述事项在用户确认后有明确版本、引用和可见变更记录；对无法确认的事项标记 `PENDING_DECISION` 并限定它阻断的具体设计范围。不是要求所有未来问题必须提前回答，也不是为了冻结而猜测数据表或 Schema。

### S4 退出检查

用户审阅并批准本次需求范围与验收；S1/S2 事实采用的源码和证据版本明确；需要改变的旧结论被正确区分为历史与当前；本次技术方案的关键约束与开放决策清楚。**未得到该批准，S5 只可做不具约束力的预研，不能宣称正式设计冻结。**

## 9. S5｜基于正式输入比较方案、决定复用并冻结 V2 设计

只有此时才为某个能力做“留/改/换/不做”的正式判定；应先比较**要解决的本次问题及现有底座**，再选择实现：

1. **本次需求与证据映射**：需求 ID → S1 当前实现或缺口 → S2/S3 可借鉴的经验/反例 → 风险。
2. **方案对比**：优先评估官方已有实现，再比较适配、局部重构或新建能力。列出边界、调用成本、状态与恢复、开发成本、风险、对用户体验的影响。
3. **确定继承类型**：继承业务原则、复用当前实现、复用经过证实的局部方法、重写旧实现、舍弃不适用机制、延期非当前需求，或保留待验证；**每项决定给出证据和理由**。
4. **设计关键契约与责任**：只有需求实际需要时才决定 Context/Spec、Scene/Shot、Agent/Provider、Material、Workflow Owner、存储与版本、Hypit、Quality、UI、预算与授权等具体形态；不为了满足旧名词逐个建立模块。
5. **实施与验收路线**：从真实可审阅视频的最小纵切面规划，明确必要的正确拒绝/冷恢复及不可绕过的成本/权益条件，然后再扩展确认的产品范围。

典型评审结论应可回答：“为什么当前代码不能直接复用？”“历史经验支持哪条原则？”“另外两种方案为何不采用？”“复杂度是否被实际业务需要证明？”“怎么验证设计满足本次需求？”

### S5 退出检查

业务职责、接口、数据权威、恢复/幂等、Rights/预算及关键非功能约束与正式需求相容；主要取舍经评审并有必要 ADR；可观察验收已覆盖成功、合法失败与恢复；用户批准正式设计。然后才允许推进 S6 实施（仍按付费、权限、真实服务单独授权）。

## 10. 后续 S6–S7：真实交付与逐步优化

- **S6 实施和首条真实用户作品**：按 S5 冻结的最小产品路线实施；严格记录 Web 用户确认、所加载版本、实际模型/素材/权益、制作过程、真实 MP4、审片/反馈和故障恢复。不能用离线生成的 MP4、固定回执或人工修改产品源码冒充端到端 Creator 自主成功。
- **S7 质量、效率与确认范围验收**：在真实结果上衡量调用、耗时、失败率、用户打断次数、局部修订与跨主题风格等，再决定合理的性能优化和长片/音轨等扩展。产品范围只以 S4 正式确认版本为准。

## 11. 交接、准入和反偏移检查

进入任何下一阶段前，交接须简明标记：

| 字段 | 写法 |
|---|---|
| 阶段与成果 | `S2/S3/S4/S5`、`COMPLETE/PARTIAL/BLOCKED`，说明此状态具体证明什么 |
| 证据与版本 | 固定源码 SHA、历史项目/Attempt/Operation、必要文档与回执、具名验收结果 |
| 已知事实 | 哪些确实被证明，哪些只是软件、局部、离线或历史 |
| 归因/决策层级 | 事实、支持归因、假设、历史认识、本次用户已批准决议分开 |
| 仍存在的不确定性 | 反证、未验、权限、成本、安全与下一步需要的确认 |
| 下一动作 | 只提出**当前已获授权**的最小后续阶段任务，不以 Task 自行扩大权限 |

**四个阶段偏移警报：**

- S2 把历史缺陷写成“V2 立刻修复”或把 `ModelGateway` 等候选变成架构标准；
- S3 将“历史有效需求”“工程实现约定”直接写入本次 `01_REQUIREMENTS.md` 作为已批准事项；
- S4 用户需求未确认，就按 V1 旧 `900s`、声音模式、旧协议或局部测试去评判 V2 必须实现；
- S5 方案未比较 S1 官方现有能力和 S2 的正反证据，就以抽象完整性推动新 Agent/Gate/状态机。

**当前工作停点**：本文件只确立研究和设计流程。现有 S1-A/S1-B PR 尚未合入，新历史复盘尚未完成；S2 研究结论、S3 经验与历史需求、S4 正式需求、S5 V2 技术方案均不得标记为已完成或已冻结。实际完成范围以对应 PR、固定证据及用户验收决定。
